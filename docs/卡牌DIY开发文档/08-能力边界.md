## 1. 四级定义（互斥，只选一个）

| 层级 | 含义 | 判据 | 你该怎么办 |
| --- | --- | --- | --- |
| **内核缺** | 内核没有该能力，游戏层补不了 | 需要的符号在内核不存在 | 换机制，或提内核改动 |
| **游戏层未接线** | 内核有能力，游戏层未暴露/未接上 | 符号存在但 `internal`、未注册或未落到流程 | 用公开替代路径；或提游戏层改动 |

## 3. 逐条展开（必读 5 条）

### 3.1 G-01 原生指令卡没有反制窗口——**已解决（P4）**

**原现象**：`OrderCard` 的打出链是「预打出 → 打出宣告 → 主动 handler → 收尾」，不调用 `OrderFlow`；因此注入 `OrderFlowBands.Counter` 的反制效果收不到普通指令。

**现状**：原生指令卡改由 `PlayManager.PlayOrderAsync` → `IOrderAction.ExecuteAsync` → `OrderFlow` 施放，段序 `Counter(1) → Resolve(2) → Finalize(3)`：

```csharp
// 施放方：原生指令卡（PlayManager 自动接入，不需要手写 OrderFlow）
await match.PlayManager.PlayOrderAsync(orderCard, ct);

// 反制方：Counter 段 handler（默认命中＝Stop：指令照常扣费/离手，效果不触发）
private Task OnCounter(OrderFlowView view, Context ctx, CancellationToken ct)
{
    ctx.Stop(); // 只停其后各段：Resolve（含 card.played）跳过、Finalize 照常
    return Task.CompletedTask;
}
```

语义（P4）：

- **`Counter`**：反制卡激活时把效果 handler 注册到此段；命中默认 `ctx.Stop()`（指令**照常扣费、照常离手**，只是效果不触发），`ctx.Interrupt()` 为可选严格中断（牌留手、不扣费）。
- **`Resolve`**：priority 0 发 `card.played`，priority 100 按登记序执行全部主动效果（`ICastAction`）；被 `Stop`/`Interrupt` 时整段不执行——**被反制的指令不发 `card.played`**（视为未成功打出，这也是现有「被动效果 hook `card.played`」不触发的原因）。
- **`Finalize`**：扣费 → 离手（`Stop` 不阻止、`Interrupt` 阻止）。

**边界提醒**：反制卡一次性消耗——命中即从手牌移除并走弃置（`card.discarded`）、注销 Counter 段 handler、回到未激活、**不退费**；反制计数仍是效果实例状态（如 `_orders`），多张同类反制各自计数。

**历史**：P4 之前要反制只能把指令改写成 `ICastAction` 再显式 `OrderFlow.ExecuteAsync(...)`；该写法仍可用于自定义施放，但不再是绕开缺口的唯一手段。

### 3.2 G-02 战斗入口——**已解决（R10）**

**原现象**：`EffectRuntime` 的动作表里没有「发起战斗」；作者只能两向 `DamageAsync` 逼近。

**现状**：`EffectRuntime.BattleAsync(first, second, source = null, ct = default)` 已上线：

```csharp
var runtime = EffectRuntime.ResolveFor(unit);
await runtime!.BattleAsync(unit, enemy, source: unit, ct);
```

语义（R10）：

- **快照＋同时结算**：先各自快照攻击力有效值，再依次 `battle.damage` → `damage.apply`；先死者不影响反向输出。
- **归属**：`first → second` 的伤害 `Source/Killer = first`，反向同理；`source` 只是「谁发起了这次战斗」的审计参数。
- **前置**：双方均为在场存活单位；否则 `false` 且零副作用。
- **不做**：射程/守护/烟幕/拦截/伏击改写/反击资格判定；不扣行动费、不清行动位；
  不发 `unit.attack.*` / `unit.combat.survived` / `unit.acted`。
- **与指挥对战的差异**：指挥对战＝`unit.attack` 流程（合法性＋反击＋伏击）；战斗＝纯对拼，只保留伤害层通用改写（免疫、战斗类改写）。

**仍存在的半条缺口**：撤退没有 `EffectRuntime` 动作面方法——用 `CommandManager.MoveUnitAsync(unit, slot, ct)`（限己方支援线空槽；S6 起不扣费、不动行动位）。

### 3.3 G-03 数据侧改写的段位——**已解决（v4）**

**原现象**：旧预制体可以声明 `injects[{ target, band, event, priority }]`，但 `band` 非空会写一条隔离记录并跳过该注入，只有默认区段可用。

**现状**：旧 `injects` 整条通道已随触发器退役。v4 用两层表达：

| 想做的 | 写法 |
| --- | --- |
| 在成员**外围**改写（先于/后于整条边集合） | `wraps[]` ＋ `phase: before/after/replace` |
| 在**成员内部**的某个段落地 | `members[].band`（段名）＋ `members[].bands`（段序方案） |
| 在 handler **内部**某点插入 | `members[].seams` ＋ `wraps[].seam` |

```jsonc
{
  "members": [
    {
      "name": "onCombatDamage",
      "band": "Initiate",                       // 落在这套方案的首段 → 天然先于转发
      "bands": ["Initiate", "Announce", "CounterGuard", "Counter", "Adjust", "Commit"],
      "handler": { "id": "diy.armor#onCombatDamage", "script": "…" }
    }
  ],
  "wraps": [
    { "target": "engine#damage-apply", "phase": "before", "handler": "diy.armor#onApply" }
  ]
}
```

**需改哪里**：无。

**边界提醒**：段名必须出现在自己的 `bands` 方案里，否则装载期 `structure` 失败。
三套合法方案见 02 章 §5.2（`ActionTrigger`／`ActionHandle`／`OrderFlow`）。

### 3.5 G-05 targeter 候选来源限制

**现象**：交互式选靶的候选由调用方（后端）在 `ReferenceSetParameter` 里给出；数据侧没有「注册候选提供器」的公开面。

**层级**：部分可覆盖。

**替代写法**：

1. 不需要玩家点击 → `EffectRuntime.SelectAsync`（无头选靶，判定器求值）；
2. 需要玩家点击 → 代码侧 `TargeterManager.ResolveFor(card)` + `RunAsync`，自己收集候选（见 [04](./04-目标选择targeter.md) §6）；
3. 候选的「动态合法性」用 `domainValidator` 表达（如仍在手牌、仍存活）。

**需改哪里**：提供按槽位/tag 的候选提供器注册面，让数据侧只声明「筛什么」。

### 3.6 G-08 残留：外来边在资产层不能定段

**现象**：`members[].band`／`bands` 允许作者给自己的**自有边**挑段，但 `mounts[]` 只有 `target` 与 `member` 两个字段——
资产层无法指定「这条外来边落在目标的哪一段」。

**后果**：外来边恒与目标成员的自有边同段，并排在自有边之后。想「改写先于落地」只能：
用 `wraps[]`（包装在外围，天然先于整个边集合），或转代码侧（`SubscribeMember(..., band:)`／`AttachMemberEdge(..., band:)`）。

**层级**：部分可覆盖（不是内核缺——`MountEdge.Band` 存在，只是资产 schema 没暴露）。

**需改哪里**：`AssetSchema` 的 `mounts[]` 增加可选 `band` 字段并透传到 `MountDeclaration`。

## 4. 已解决：弃置归因（R9）——**不是缺口**

历史上 `card.discarded` 只有 `{ Card, Player }`，无法判断「谁害的」。R9 已解决：

```csharp
// 施动方：弃置时显式带来源
await match.PlayerManager.DiscardCardAsync(player, card, ct, source: enemyCard);

// 监听方：读事件引发者（不是 TriggerCard）
// view.Source == enemyCard
```

- 读法：`view.Source` 判「敌方所致」；`view.TriggerCard` 判「当前 handler 是谁触发的」。
- 证据：`TriggerSourceSignalTests.Discarded_Carries_Source_On_Payload_And_View` / `Discarded_By_Enemy_Triggers_Discarded_By_Self_Does_Not`。
- 因此本表**不再**列「弃置无归因」；若在旧文档/示例看到，以本节为准。

## 4.1 R11 行为变更（不是缺口，是已确认的行为调整）

**变更**：免疫从「对战流程内的归零」迁到 `damage.apply`（伤害处理端），因此**效果伤害与战斗伤害也会被免疫归零**。此前免疫只挡对战伤害。

| 组合 | R11 之前 | R11 之后 |
| --- | --- | --- |
| 对战伤害 × 免疫 | 归零 | 归零（不变） |
| **效果伤害 × 免疫** | **穿透（照常扣血）** | **归零**（行为变更） |
| **战斗伤害 × 免疫** | 不存在 | **归零** |
| 重甲 × 对战伤害 | −X | −X（不变） |
| 重甲 × 效果/战斗伤害 | 不减免 | 不减免（不变；重甲只挂 `combat.damage`） |

**为什么改**：R11 要求「处理端是唯一扣数值处，全局改写（免疫归零）挂处理端」；免疫若留在对战触发端，就必然漏掉效果/战斗两类伤害。

**影响**：卡面写「不会受到伤害」现在名副其实；只写「不会受到对战伤害」的旧卡需要改成重甲，或用 `wraps[]` 在 `engine#combat-damage` 上注册自定义改写。

**补充（数据侧可达）**：伤害四端是引擎成员，`wraps[]` 可直接挂上去
（`engine#combat-damage` / `engine#effect-damage` / `engine#battle-damage` / `engine#damage-apply`）。
「受到的伤害 -N」这类持续减伤因此**不需要写 C#**——见 [示例 09](./examples/09-相邻掩护.md)。

**证据**：`DamagePipelineTests.Effect_Damage_Is_Zeroed_By_Immune` / `Battle_Damage_Is_Zeroed_By_Immune` / `Armor_Does_Not_Reduce_Effect_Damage` / `Armor_Does_Not_Reduce_Battle_Damage`。

## 5. 使用规则

1. 先查本表编号；命中就按「现状替代写法」做，不要绕道私有 API。
2. 替代写法有已知差异的（G-05、G-11；G-02 已由 R10 关闭），必须在卡面/README 标注差异，不假装等价。
3. 写不出替代的，把「需改哪里」写成**最小改动点**（一个方法/一个字段），不要写「需重构」。
4. 每条缺口只能有一个层级；跨层拆条。
