# Requirements — 多人支持（服务端 / 客户端分离）

> 状态：**需求 grill 第 1 轮**（仅 Q1 已发出，其余待对齐）。决策来源与代码基线见 `requirements-grill-plan.md`。
> 验收形态、客户端边界、服务端粒度、传输协议、权威模型均**未定**，本文档随 grill 逐轮沉淀。

一句话：把 OrC 逻辑引擎从客户端进程内抽出，做成独立服务端；Godot 前端退化为纯客户端，两者之间只通过字符串形态的远程协议交换"动作请求 / 视图投影 / 事件段 / 选靶请求应答"，从而支持多个客户端接入同一对局。

## Scope

- Includes（暂定，待 Q1–Q9 确认）：
  - 服务端进程承载逻辑引擎与对局生命周期。
  - 客户端进程不再直接持有或调用引擎对局对象。
  - 一条字符串/远程协议：动作、投影、事件段、选靶、生命周期。
  - 至少两个客户端可接入同一对局（具体形态待 Q1）。
- Excludes（暂定）：
  - 匹配/房间/账号/排行榜/生涯数据（待 Q8 确认）。
  - 观战/回放（待 Q1 确认）。
  - 引擎内部逻辑（触发器、效果、判定器）的规则变更。
  - 卡牌数值与平衡调整。

## Constraints

- 引擎侧硬约束（现状，需确认是否允许改动）：
  - `MatchExecutor` 单进程只允许一个活跃对局（`Attach` 抛异常）。
  - 选靶桥交付**活会话对象**，`SelectorEvent` 装 `Ref<Entity>`：选靶必须在服务端终结，对外只能暴露序号/引用键。
  - 引擎全域无锁单线程语义，靠"不并发"保证；任何跨进程入口不得引入并发进入引擎。
  - `LogEntry.Data` 是活对象图，现有 JSON 降级丢失身份，不可回解。
  - 投影必须吃活 `Match`/`Player`：投影只能在服务端算。
- 前端侧硬约束（现状）：
  - `proto/ui/**` 零引擎引用且有运行时守卫，必须保持。
  - `proto/contracts` 已是纯 DTO，可作为协议载荷基础。
  - 桥接层与构建均硬依赖引擎源码树；客户端要"只依赖协议"必须解耦。
- 术语以 `CONTEXT.md` 为唯一称谓来源；"统一引用""段""投影""对局执行器""引擎托管引用表"等既有术语不得另造同义词。

- Status: **Pending（Q2、C3）**

- Status: **Pending（Q3）**
