## 二、缺陷清单

### P0 — 安全 / 裁决可信度（均已实证）

#### P0-1 跨座位读取对手手牌，并劫持对方推送流 ✅ 已修复

- **位置**：`src/Orc.Mcp/Tools/ObserveTools.cs:189`（`seat` 取自调用参数）→ `:203`（直接投影）；`src/Orc.Server/Transport/ServerHost.cs:327-357`（`BindSeat` 无条件信任返回值里的 `seat`）。
- **现象**：座位 0 的会话调用 `observe.view { seat: 1 }`，得到座位 1 视角的完整投影（`selfHand` 即对手手牌明细，含 `cardId`）。
- **实证**（座位 0 客户端发起）：
  ```
  CROSS_SEAT: ok=True, returnedSeat=1, selfPlayerName=我方, selfHand=5
              [pack/ai.sample/ai.sample.infantry ×5]
  ```
- **二次伤害**：`BindSeat` 会把该会话的 `Seat` **永久改写为 1**。随后真实推送的 `notify/view` 全部变成座位 1 视角：
  ```
  REBIND: pushes=1, seats=[1]     // 房主会话此后收到的是对手视角
  ```
- **影响**：① 任何已连接客户端可实时偷看对手手牌；② 可把对手的推送流"抢"过来（对手客户端收不到自己的 view）；③ 违反文档 §10.4「对手手牌根本不在投影里」与 §1「服务端负责规则裁决」。
- **建议**：`session.Seat` 只能由 `room.claim` / `room.resume` 的成功结果写入（`ServerHost` 显式识别这两个工具）；`observe.view` 忽略 `seat` 参数、强制用会话座位；若未绑定座位则拒绝。

#### P0-2 动作归属座位可伪造（替对手认输 / 出牌 / 换牌 / 选靶） ✅ 已修复

- **位置**：`src/Orc.Mcp/Tools/MatchTools.cs:26-43`（`match.concede {owner}`）；`src/Orc.Mcp/Tools/PlayerActionTools.cs:49-58`（`mulligan.done {owner}`）、`:72-85`（`play.unit {ref, owner, slot}`）；`src/Orc.Mcp/Match/TargeterBridgeAdapter.cs:275-323`（`Submit` 只做先到先得，无座位校验）。
- **现象**：`owner` 完全由客户端指定，服务端没有任何「该会话是否拥有该座位」的校验；`target.submit` 同样不校验提交者座位。
- **实证**（座位 0 替座位 1 认输）：
  ```
  CONCEDE: ok=True, code=ok, hostOutcome=Win, guestOutcome=Lose
  ```
- **影响**：座位 0 一行调用即可让对手认输直接获胜；同理可替对手确认换牌、替对手出牌（`ref` 可由 P0-1 获得）、抢答对手的选靶请求。这使"服务端裁决"在多人场景下形同虚设。
- **建议**：在 `ServerHost.HandleToolsCallAsync` 建立统一门禁——动作类工具的 `owner`/`seat` 参数必须等于 `session.Seat`（`match.end_turn` 由引擎判当前方，无需参数）；`target.submit` 需要校验 `pending.Seat == session.Seat`。AI 走 `IAiMatchGateway` 不受影响。

#### P0-3 房主身份可被任意客户端抢占；房主缺失时开局无需令牌 ✅ 已修复

- **位置**：`src/Orc.Server/Room/Room.cs:410-416`（`NormalizeKind` 把任意 `kind` 归为 remote，但 `"local"` 被直接接受）；`:217-236`（`HostSlot()` 为 `null` 时**跳过**令牌校验）。
- **现象**：① 局域网内任何客户端可在 seat 0 空着时 `room.claim {seat:0, kind:"local"}`，即刻获得开局/踢人权限；② 房主在 lobby 断线后座位被立即释放（`ServerHost.cs:360-377`），`HostSlot()` 变为 `null`，此后**任何人**可 `room.start`。
- **影响**：房间控制权可被抢；房主断线后房间失去唯一权威来源。文档 §1 定义 `local` 为「房主本人」，实现未做来源约束。
- **建议**：`local` 只允许来自回环地址（`session.RemoteEndPoint` 判定）；`HostSlot() is null` 时 `room.start` 返回 `unauthorized`，或把房主令牌在进程内固定（不随座位释放）。

### P1 — 功能缺口 / 契约违反

#### P1-1 AI 行动、断线判负都不推 `notify/view`（客户端表现为"卡住"） ✅ 已修复

- **位置**：`src/Orc.Server/Transport/ServerHost.cs:296-309` 是 `PushViewsAsync` 的**唯一**调用点（且仅当 `IsMatchAction` 且 `outcome.Ok`）；AI 驱动 `:526-605` 直接走 `IAiMatchGateway`，绕过该路径；`CheckDisconnectGrace` 的 `ConcedeAsync`（`:418`）同样不推送。
- **实证**：房主结束回合后 AI 完成一整回合（`turn 2 → 3`），期间 `notify/view` 只增加 **1** 条——那是 `match.end_turn` 本身触发的，AI 的每一步都没有产生 view。
- **影响**：Godot 客户端按文档 §10.2「状态靠 `notify/view`」实现时，AI 回合画面完全不动、断线判负后也不显示终局；文档 §13「AI 回合不动」的排查项实际是**必现**行为。
- **建议**：在 `DriveAiAsync` 每步成功、`CheckDisconnectGrace` 判负后、以及超时取消选靶后调用 `PushViewsAsync`（注意需在串行队列上下文内）。

#### P1-2 断线发生在对手回合 → 断线方永远不会被判负 ✅ 已修复

- **位置**：`src/Orc.Server/Transport/ServerHost.cs:380-423`。宽限检查**先** `TryRemove` 断线记录、**再**判断是否轮到该座位；不轮到时直接 `return false`，记录已被删除。
- **实证**：断线发生在房主回合（`activeSideBeforeDisconnect=self`），跨过一次宽限检查后房主结束回合：
  ```
  GRACE: phaseAfterTurn=play     // 期望 over：断线方未被判负，对局永久卡在断线方回合
  ```
- **影响**：对手掉线且当时不是他的回合 → 对局永久挂起（除非重连）。这是最常见的掉线时序。
- **建议**：先判断回合归属，仅在真正认输后再移除记录；或保留记录并标记 `attempted`，下一次检查重试。

#### P1-3 客户端心跳只存在于配置，没有任何实现 ✅ 已修复

- **位置**：`src/Orc.Client/ClientOptions.cs:17-21` 定义 `HeartbeatInterval` / `HeartbeatTimeout`；`OrcClient.cs` 全文无定时器、无 `ping` 调用。
- **违反**：文档 §4.3「客户端：静默超过 30 秒主动 `ping`」、§9「30s 发 `ping`；45s 无响应即判定断线」。
- **影响**：TCP 半开（拔网线、NAT 超时、休眠）无法被客户端发现，`CallAsync` 会一直挂起直到服务端 45s 超时关闭；客户端 `IsConnected` 仍报 `true`。
- **测试假覆盖**：`tests/Orc.Server.Tests/SkeletonSmokeTests.cs:34-40` 名为 `ClientOptions_Defaults_MatchHeartbeatDecision`，实际只断言两个默认值，零行为覆盖——容易被误读为"心跳已实现"。
- **建议**：在 `OrcClient` 启动空闲计时器（收到任何帧即重置），超时后发 `ping` 并在 `HeartbeatTimeout` 内无响应则关闭连接、`FailAllPending`。

#### P1-4 房间态没有推送，座位面板只能轮询 ✅ 已修复

- **位置**：`src/Orc.Protocol/InitializeMessages.cs:35` 定义了 `notify/room`，**全仓无发送点**（`grep` 仅命中常量声明）。
- **影响**：客人 `room.claim` / 断线释放座位后，房主端不会收到任何通知，座位面板不会更新；而文档 §10.2 明确要求「不要轮询」，§2.3 要求座位面板显示 `ready`/`connected`。两者无法同时满足。
- **建议**：`Room` 状态变更时向所有会话广播 `notify/room`（载荷 = `room.info` 的 details），或明确在文档中承认房间态需轮询。

#### P1-5 `seats[].ready` 恒为 `true`，没有就绪语义 ✅ 已修复（字段已删除）

- **位置**：`src/Orc.Server/Room/Room.cs:78` 固定传入 `true`；`SeatSlot` 无 `Ready` 字段。
- **影响**：文档 §6.2 把 `ready` 列为客户端状态源，§13 又用 `room-not-ready` 表示"座位未满"——实际含义只是"有控制器"。客户端无法表达"我还没准备好"。
- **建议**：要么补 `room.ready` 工具与字段，要么在文档中删除 `ready`（改为由 `controllerKind != ""` 推导）。

## 三、测试审查

### 3.1 有效性强项

- `RawProtocolContractTests`（6 例）手写 JSON、不经过共享 DTO，能抓住"客户端与服务端一致地写错字段"这类系统性缺陷；这是本批最有价值的测试设计。
- `RoomTests` 覆盖了 claim/start/kick/resume 的主干与错误码；`SerialWorkQueueTests` 覆盖优先级与容量拒绝；`CrossSeatTargetingTests` 覆盖选靶推送的座位路由（含 `target.expired`）。
- `ProtocolEnvelopeTests` 对信封形状、错误码数字做了逐字段断言。

### 3.2 关键盲区（按风险排序）

| 盲区 | 现状 | 后果 |
|---|---|---|

### 3.3 弱断言与同义反复

1. `tests/Orc.Server.Tests/EndToEndTests.cs:77-79`
   ```csharp
   Assert.NotEqual(matchId + ":0", matchId + ":1");   // 恒真，零信息量
   ```
   原意是"两视角投影分别生成"，但后缀写死不同；即使两边 `matchId` 与内容完全一致也通过。应改为断言 `selfHand` 不相交、`selfPlayerName` 不同。

2. `tests/Orc.Server.Tests/ServerProcessTests.cs:56`
   ```csharp
   await server.DisposeAsync();
   Assert.True(server.HasExited);   // Dispose 后 HasExited 被 catch 成 true，恒真
   ```
   `HasExited` 的 getter 捕获 `InvalidOperationException` 返回 `true`，该断言无法区分"正常回收"与"根本没启动"。

3. `tests/Orc.Server.Tests/ResilienceTests.cs:34-38`、`:62-66`
   只断言"异常不是 `TimeoutException`"，`ObjectDisposedException` / `NullReferenceException` 都能通过。应断言 `IOException` 且 `InnerException` 为连接关闭原因。

4. `tests/Orc.Server.Tests/ResilienceTests.cs:124-144`（`ConcurrentRequests_FromTwoClients_AreAllServed`）
   同一连接内的请求由服务端读循环串行处理，50 并发实际不并发进入引擎；用例名暗示的"并发安全"未被验证（真正需要验证的是两个座位同时动作时的门禁）。

### 3.4 脆弱性

- `ServerProcessTests` 依赖 `dotnet run --no-build` + 仓库布局 + 90s 超时，在 CI 容器/无 SDK 环境会整组失败；建议标记为 `[Trait("Category","Process")]` 并与主套件分离。
- `AiAndDisconnectTests` 用 `Task.Delay` + 250ms 轮询等待 AI，AI 节奏由 `150/300ms` 硬编码，机器负载高时易 flaky（实测单次 5–20s）。
- 大量 e2e 用 39 张同名卡 + `EnforceDeckRules = false`，绕过了 `DeckRules`；卡组规则本身的覆盖只在 `DeckRulesTests` 单测里，端到端链路没有"合法 39 张卡组"的用例。

## 六、修复验收（2026-10-21）

### 6.1 授权层形态

`ServerHost` 新增集中白名单（`SeatScopeRegistry`，四类 ＋ 两个专门分支），门禁顺序固定为 **分类 → 座位校验 → 入队**，表外工具一律 `unauthorized`（默认拒绝）。座位绑定收敛为唯一写入口，并显式拆除悬空绑定：

| 类别 | 工具 | 规则 |
|---|---|---|
| `Bind` | `room.claim` / `room.resume` | 成功后写入 `session.Seat`（唯一写入点），同时解绑同座位的其它会话 |
| `OwnerScoped` | `match.concede` / `mulligan.*` / `play.unit` / `play.join` | `owner` 必须等于会话座位；缺失即拒绝 |
| `SeatRequired` | `match.end_turn` / `play.*_pre` / `command.*` | 仅要求已绑定座位 |
| `Agnostic` | `room.info/release/kick/add_ai/start` / `service.*` / `docs.*` / `play.can_play` / `command.availability` | 不看座位，且**严禁**写入座位 |
| 专门分支 | `observe.view` / `target.submit` / `target.cancel` / `target.claim` | 视图强制会话座位；选靶按 `pending.Seat` 裁决；`target.claim` 保留兼容 |

绑定不变量：**一个座位最多绑定一个活动会话，一个会话最多绑定一个座位**。`UnbindSeat` 覆盖五个调用点：`room.release` / `room.kick` / `room.add_ai` 成功、lobby 断线 `DropSeat`、`Bind` 时同座位其它会话。
