# Requirements — 编排实体化（Orc 引擎重构）

把 Orc 的编排从「效果主触发器 + 名字字符串挂载」重写为「实体／预制体（类）+ 成员 handler 挂载」，
目标：**新增效果不再需要模板代码**，且编排结构具备 OOP 的封装／继承／多态能力。

Status: **Confirmed — 需求 grill 已收敛（2026-10-26），待用户最终定稿确认**

---

## 0. 现状基线（代码事实，非需求）

### 0.1 效果装载是「主触发器 + 文本声明挂载点」

`Effect.ExecuteMount`（`src/Orc/Cards/Effect.cs:332`）固定四步：

```
挂 disposing 触发器 → 挂主触发器（MainTrigger）→ IsMounted=true → OnMount()
```

- 主动效果（指令）**不参与装载**：不挂主触发器、不执行 `OnMount`（`Effect.cs:44`）。
- 装载之外的扩展只能靠两种文本声明：
  - `hooks: ["card.played"]`（`mainTrigger.hooks`）——总线挂载靠**名字字符串**匹配；
  - `injects: [{ target: "伤害处理触发器", band: "Rewrite", event: "onDamageApply" }]`
    （`samples/card-pack-diy/effects/diy.adjacent-cover.mitigation.prefab.json`）——注入靠**触发器显示名字符串**定位。
    重命名目标触发器即静默断链，无编译期/装载期校验。

### 0.2 一个触发器只有一个视图类型

`Trigger<TView>` 是泛型类，`viewType` 在预制体里直接写 C# 类型全名
（`"viewType": "Orc.Cards.CardEventView"` / `"Orc.Game.Damage.DamageApplyView"`）。
想看第二种数据形状 → 必须再建一个触发器（文档《02-触发器与handler》§9 边界明确承认）。

### 0.3 主动／被动二分贯穿四层

| 层 | 表现 |
| --- | --- |
| `TriggerKind` | `Active` 不可挂载、`Passive` 无 `hooks` 不可 `Bus.Mount` |
| 效果基类 | `PassiveEffect`（装载／`OnMount`）vs `ActiveEffect<TView>`（施放／不装载） |
| 预制体 | `kind: "passive"` / `kind` 缺省为 active |
| 断言路径 | `Effect.cs:394`、`:486` 处按 `Kind == Passive` 分支 |

### 0.4 触发器实例化点分布（40 处 `new Trigger<`）

| 文件 | 数量 | 归属 |
| --- | --- | --- |
| `Orc.Game/Commanding/CommandManager.cs` | 7 | 游戏层流程 |
| `Orc.Game/Cards/UnitCard.cs` | 7 | 卡牌实体的具名成员（部署／加入／单位化／老兵／揭示／指向／打出） |
| `Orc.Foundation.Actions/*.cs` | 15 | 动作触发端／处理端 |
| `Orc/Cards/OrderFlow.cs`、`Effect.cs`、`CardLifecycle.cs` | 6 | 内核 |
| 其它（Hq／Retrigger／Sandbox 等） | 5 | 混合 |

### 0.5 「全局触发器」是两个不同机制

| 机制 | 位置 | 语义 |
| --- | --- | --- |
| `TriggerRegistry` | 对局级（`Match.TriggerRegistry`） | 分层（`LowLevel`/`External`）登记，**只记账**，不参与挂载 |
| `OrchestrationManager` | 引擎级（`LogicEngine.Orchestration`） | 全量登记（含卡上效果主触发器），供审查链 `BuildAuditChain` |

### 0.6 targeter 与判定器是两套互不相干的机制

| | 判定器 | targeter |
| --- | --- | --- |
| 形态 | `Judicator.Invoke(object[]?)`，**同步**、无状态 | `ITargeterFlow.Step/Retry`，**异步挂起** |
| 数据 | 调用载荷 | `Selector` 队列 → 前端 `NextAsync` 拉取 → `target.submit` 提交 |
| 可改写 | 是（`JudicatorRegistry` moding） | 否 |
| 无头可用 | 是 | 需要"前端"（含脚本前端）应答 |

### 0.7 现有术语的冲突点

| 术语 | 现有定义（`CONTEXT.md`） | 本需求要的新语义 | 处理 |
| --- | --- | --- | --- |
| 触发器 | "纯编排节点：只负责事件排序与调用，**不承载业务逻辑**"（§99） | 带嵌入逻辑（视图／合法性／顺序调用）的 handler | 待仲裁 |
| handler | "触发器内的注册项"（`Register(name, handler, band, priority)`） | 无嵌入逻辑的可执行节点（＝原被动触发器） | 待仲裁 |
| 实体 | `Orc.Core.Entity`：具名、可终结、可安全引用；卡牌／单位／玩家继承 | 引擎／卡牌／handler 三类的统称 | 扩展，不冲突 |
| 预制体 | 效果／触发器的数据形态（`EffectPrefab`／`TriggerPrefab`／`EventPrefab` 三层） | 实体的**类**（OOP 模板），可继承、可实例化 | 语义升级 |

## 1. Scope

- **Includes**：
  - 内核编排抽象的重写：实体（引擎／卡牌／组件／handler）、预制体（类）、成员 handler、挂载与可见性、视图投影、初始化触发器；
  - 效果从 `Effect` 类降为"组件实体的成员集"，组件自托管装配与注销；
  - targeter 并入判定器体系，统一提交通道，`random` 归引擎随机服务并限制使用；
  - 引擎实体承载原"全局流程触发器"；
  - 审查面从触发器种类图改为实体—成员—挂载边图；
  - 游戏层 40 处触发器实例、151 个资产、`Orc.Protocol` 选择器消息的迁移。
- **Excludes**：
  - 判定器（27 条内置）与资产服务的**判定逻辑语义**不变（只改挂接方式）；
  - 卡牌数值／平衡／KARDS 规则语义；
  - `components` 数据组件（`factionCost`/`battleStats`/`tagData`/`keywords`）的形态与加载链；
  - UI 表现层与美术投影（`Orc.UI`）；
  - 卡牌数据的持久化存储格式（只改效果／触发器 schema）。

## 2. Constraints

- **纯文本预制体**：不得为表达"类"而新增 C# 类；OOP 三特性由文本 + 既有机制模拟。
- **可审查**：审查面能力不得退化（R7）。
- **初始化期不执行业务逻辑**（R6）：装配声明驱动，业务逻辑在成员 handler 中。
- **成员 handler 全局一份**（R4）：禁止 per-instance 状态；状态只能落在 owner 实体字段或数据面。
- **每批全绿**：迁移批次内不得留下红测试（R8）。
- **资产不兼容**：新 schema 不做旧格式兼容读取，迁移器负责转换（R8）。

## 3. Requirement Items

### R1: 触发器与 handler 合流
- Status: Confirmed
- Scenario/Trigger: 作者要新增一个"在某流程里插入逻辑"的效果。
- Behavior: 触发器本质是特殊 handler——可被挂载在其它触发器上；其嵌入逻辑固定为「上下文视图 + 合法性检验 + 按顺序调用挂载的 handler」。`Active`/`Passive` 二分被抛弃：原主动触发器 = 新触发器，原被动触发器 = handler。
- Acceptance:
  - [ ] 模型里不存在"主动／被动"分类字段
  - [ ] 任意触发器可被挂载到另一触发器上，且保留自己的视图与合法性检验
  - [ ] 挂载项按声明顺序确定执行序，无隐藏优先级通道
- Terminology: 触发器、handler、挂载

#### R1a: 上下文视图的形态（已确认：方案 C）
- Status: Confirmed
- Scenario/Trigger: 作者要让一个触发器读到执行上下文里的数据。
- Behavior: 视图是触发器内的**字段清单声明**（文本），由 ctxViewer 按名从数据面投影；字段类型限**封闭内建集**（实体引用 / 数字 / 字符串 / 布尔 / 以上数组）。不支持嵌套结构，需要复杂计算时退回 csx。
- Acceptance:
  - [ ] **不为每个数据形状新增 C# 类**（允许且仅允许一个通用承载类型，见下）
  - [ ] 必填字段缺失＝装载期 fail-fast（不进入执行期）
  - [ ] 字段类型超出封闭集＝预制体装载期拒绝
  - [ ] 嵌套结构不可表达（显式不支持，而非静默降级）
  - [ ] csx 里引用未声明字段＝装载期**静态语法检查**报错（给出字段名 + 行内片段）
  - [ ] csx 里写只读字段＝装载期拒绝（静态检查）+ 运行期拒绝（写入闸门）
- Terminology: 视图、封闭类型集、ctxViewer、承载视图
- 决策记录: 2026-10-25，用户在 A（纯文本投影）／B（保留 C# 视图类）／C（混合封闭类型集）中选 C。
  理由：视图本质是按名取值，`ContextViewBinder` 已按名绑定 `ctx.Data`；移到预制体只是声明位置变化。
  A 被否：会在文本里长出一门半吊子类型系统。B 被否：仍要写 C# 类，等于保留模板代码来源。
- **定稿澄清（作用域）**："不新增 C# 类型"指**不为每个数据形状新增类**，允许存在**一个通用承载类型**承接全部形状
  （否则 csx 没有可书写的第一参数）。csx 入口签名：
  ```csharp
  Func<dynamic, Context, CancellationToken, Task> HandleAsync = async (view, ctx, ct) => { ... };
  ```
  承载视图实现动态成员读写（**名字空间仅限数据面／视图声明字段**），`view.Host is Orc.Cards.Card` 这类转换语义不变
  （取到的就是真实实体对象）。字段名拼错由**装载期文本扫描**兜住，而非编译期。
- **实现提示**：现有 disposing 规则在 `Effect.NormalizeDisposalHooks` 与 `EffectPrefab.NormalizeDisposingTrigger`
  写了两遍（漂移源）；新模型只保留预制体层一处，由框架统一合成边。
- **沙箱口径**：`Microsoft.CSharp` 进入 `Orc.Script` 的 `AllowedAssemblies`（`dynamic` 绑定器所需）。
  它只提供 DLR 绑定能力，不扩大类型可见面——白名单内的 `Orc`／`Orc.Game` 类型本就可直接访问其公开成员；
  关键字过滤仍是文本级过滤，`dynamic` 不绕过它。
- **csx 失败面**：编译失败 ＝ **拒绝装载／拒绝注册（fail-fast）**，不再降级为"隔离记录 + 成员缺失"。
  - **编译时点**：前移到**预制体装载期预编译**（不保留懒编译）——"装载即验证"是 R6「漏挂不可能」的前提。
  - **爆炸半径＝卡包内原子**：一个卡包内任一资产装载失败＝**整包拒绝**；"部分成功"语义取消。
  - 卡包分**必需**与**可选**：必需包失败＝对局不开局；可选包失败＝跳过该包并在报告中标明。
  - 运行时注册（R1e）失败＝拒绝注册，错误码对齐既有 `ErrorCategory`，不留半个可寻址成员。
- **静态检查口径**（不叫"文本扫描"——用 Roslyn 语法树，`Orc.Script` 本就解析 csx）：
  - 算"写"：直接赋值、`+=`/`-=`/`++`/`--`、作为 `ref`/`out` 实参。
  - 不算：注释、字符串字面量。
  - 别名：只追踪**直接**别名（`var v = view;`），不追踪经方法/局部函数传递的 `view`。
  - **未识别形态＝放行 + 运行期闸门**，并在审查面标注"存在未经静态验证的 view 传递"。判据：误判的代价是整包拒绝（W-17），
    漏判的代价是运行期闸门生效——宁可放行并留痕，不可误杀。
  - 错误分类新增 `binding`（静态检查失败），与 `compile` / `sandbox` 区分。

#### R1b: 挂载通道与包装通道职责分离（已确认：方案 A）
- Status: Confirmed
- Scenario/Trigger: 一个逻辑需要在别人的执行里生效。
- Behavior:
  - **挂载＝设计端编排**：表达"顺序与组合"，即"这个流程里有哪些步骤、按什么次序"。
  - **包装＝元效果端修改**：表达"改写与拦截"（before / after / replace + 具名接缝），由元效果（反制、光环、减伤）使用。
  - **两条通道不可混用**：挂载不得表达"替换宿主核心逻辑"，包装不得引入新的编排步骤。
- Acceptance:
  - [ ] 混用（如挂载声明里出现 replace 语义、包装器里发起新的编排步骤）被装载期拒绝
  - [ ] 同一效果可以只用挂载、只用包装，或两者并用但职责不交叉
- Terminology: 挂载、包装、设计端、元效果端
- 决策记录: 2026-10-25，用户选 A 并给出判据："挂载管编排（设计端），包装管修改（元效果端），不能混用"。
  B（合并为相位）被否：合并会消灭"谁在什么场景该用哪条通道"的边界，反让两类作者互相误用。
  C（只留挂载）被否：改写别人结算的语义会退化为事后补救。

#### R1c: 挂载链的数据契约（已确认：方案 B）
- Status: Confirmed
- Scenario/Trigger: 子触发器被挂到宿主触发器上，执行时需要读数据。
- Behavior:
  - **装载期静态校验**：子视图字段集 ⊆ 宿主视图字段集 ∪ 子实体自有成员；不满足＝**拒绝挂载**（fail-fast，不进入运行期）。
  - **执行期投影**：按名从宿主数据面取值；必填缺失＝fail-fast。
  - **写回**：字段声明为可写时才写回**宿主数据面**（对后续步骤可见），不是子视图私有。
  - **owner 成员状态**不由该校验约束（成员默认可读自己的实体状态）。
- Acceptance:
  - [ ] 字段不匹配的挂载在装载期被拒绝，且报告缺失字段名
  - [ ] 只读字段的写入尝试失败
  - [ ] 写回在后续步骤可见（同一执行链内）
- Terminology: 数据面、投影、owner
- 决策记录: 2026-10-25，用户选 B。A 被否：视图声明退化为注释、错误推迟到运行期；C 被否：成本摊到每个挂载点。
- **定稿澄清**：视图投影只管**数据面**。经 `owner` / `owner.host` 引用直接读取实体状态（含卡牌数值、
  组件私有字段）**不受视图包含校验约束**——它们是强类型引用上的读取，不是数据面投影。

#### R1d: 挂载的寻址语法（已确认：方案 A）
- Status: Confirmed
- Scenario/Trigger: 作者要声明"这个成员挂到谁身上"。
- Behavior: 以**实体预制体 id + 成员名**寻址，形态为 `作用域#成员名`，装载期解析；目标未声明对应可见性＝拒绝挂载。
  - 三个作用域前缀：`engine#`（引擎实体）、`host#`（宿主实体）、`self#`（组件自身）。
  - **第一个 `#` 之前是作用域，之后整体是成员名**——成员名允许包含 `.`，不做任何分隔符替换。
  - 例：`engine#damage-apply`、`engine#unit.position.changed`、`host#played`、`self#on-damaged`。
- Acceptance:
  - [ ] 挂载声明不含任何"显示名"字符串
  - [ ] 目标成员不存在＝装载期报错并指出缺失的实体／成员名
  - [ ] 含点号的成员名（信号）可零转换寻址，不因分隔符替换产生同形撞名
- Terminology: 挂载、成员名、实体预制体 id
- 决策记录: 2026-10-25，用户选 A。
  B 被否：成员资产可被多个实体引用，"引用资产"≠"引用某实体上的那个成员"，归属会丢；
  C 被否：接口广播没有顺序，与 R1b"挂载管编排"直接冲突。
- **定稿修正（2026-10-26）**：原示例 `engine.damage-apply#on-before` 用 `.` 同时表示"实体"与"成员"，
  与 39 个含点号的内置信号名（`unit.position.changed` 等）冲突。改为 `作用域#成员名`，
  成员名原样保留——迁移器可机械把 `hooks: ["unit.position.changed"]` 转成 `engine#unit.position.changed`，无损可逆。

#### R1e: 信号与运行时注册（已确认）
- Status: Confirmed
- Scenario/Trigger: 某逻辑需要在"卡牌装载""卡牌销毁""单位部署"等时机被调用。
- Behavior:
  - 原 `hooks`（总线订阅）**全部改为引擎实体的成员触发器**：`card.load` → 成员名 `card.load`（寻址 `engine#card.load`）。
    **成员名保留原始点分名，零转换**（见 R1d 定稿修正）。
  - **分域**：内核基础预制体声明内核 4 个信号，游戏层 `extends` 后追加 35 个——两者在同一个 `engine` 根下合并；
    寻址解析跨层合并成员表（`engine#card.damaged` 与 `engine#card.destroyed` 分属两层声明，解析无差别）。
  - `Emit` ＝ 对该成员触发器的**调用**；"订阅"＝**挂载**到它上面——订阅不再是独立通道，模型回到 R1b 的两条通道。
  - 新增**运行时注册**能力：可向引擎注册新触发器，注册后**全局可用**、可被寻址与挂载
    （替代"必须走引用查询"才能拿到触发器）。
  - **自定义更新名**（沙盒的 `custom.placed` / `u` 等）不再走"任意字符串 Emit"，而是**运行时注册**；
    注册后才可被挂载声明引用。沙盒负责"先注册信号，再装载资产"的时序。
  - 挂载声明引用**未注册**的触发器＝明确失败（不静默、不按名兜底）。
  - 执行序：同一触发器上的挂载项按**声明序**；跨组件按**宿主预制体里组件的声明序**（静态、与装配时刻无关，
    见 R1g）。
- Acceptance:
  - [ ] 模型里不存在 `hooks` 字段
  - [ ] 所有内建时机（`card.load` / `card.destroyed` / `card.placed` / `effect.removed` 等）都是引擎实体的成员触发器
  - [ ] 运行时可注册新触发器，并立即可被挂载声明引用
  - [ ] 引用未注册触发器＝装载期错误并指出名字
  - [ ] 同一时机上多个订阅者的执行序可仅凭声明序／装载序推出，无隐藏优先级
- Terminology: 信号、成员触发器、运行时注册、装载序
- 决策记录: 2026-10-26，用户裁定："原来的 hook 全部改为引擎的成员触发器。新的机制可以是运行时向引擎注册触发器，
  以让触发器全局可用（之前必须要走引用查询）。"
  A（封闭集合）被采纳，但补以"运行时注册"作为扩展通道；C（第三通道）被否。
  执行序按装载序为父 agent 依 R1「无隐藏优先级」推出的必然结果，随本条一并确认。

#### R1h: 运行期注册与运行期挂载（已确认）
- Status: Confirmed
- Scenario/Trigger: 组件需要在初始化之后动态建立装配（条件效果、沙盒脚本、临时增益）。
- Behavior:
  - **注册与挂载是两个动作、同一门面**：注册＝创建新的可寻址触发器（信号）；挂载＝往已有触发器上挂一条边。
  - **允许往已声明的信号上运行期挂边**；这类边的顺序来源是 `appended`（**追加到末尾**）。
    `order-source` 是**边**的属性（`declared` / `appended`），不是信号或实体的属性。
  - **运行期边必须绑 owner**：随 owner 销毁自动撤销。**不存在无主永久边**。
  - **初始化期与业务逻辑的可判定边界＝数据可变性**：
    - 初始化期**可以**读装配期不可变数据（宿主类型、卡数据声明的词条、预制体声明）；
    - 初始化期**不可以**读对局状态（血量、场上单位、随机数、回合）或产生副作用/事件。
    - 因此"宿主当前拥有某词条"（运行期获得）→ 必须走运行期成员 handler；"卡数据声明了某词条"→ 可在初始化期装配。
    - 由 **API 层面**区分：初始化触发器只能拿到宿主**定义视图**，拿不到运行时视图（物理上不可越界）。
- Acceptance:
  - [ ] 运行期挂到已声明信号上的边，位次在末尾且审查标注 `order-source: appended`
  - [ ] 运行期边在 owner 销毁后不残留
  - [ ] 初始化触发器签名中不存在访问对局状态的入口
  - [ ] 声明期边与运行期边混排时，顺序可由"声明序 + 追加序"完全推出
- Terminology: 运行期挂载、运行时注册、`order-source`、定义视图
- 决策记录: 2026-10-26，父 agent 依 W-06 裁决。判据：条件装配天然存在（沙盒、临时增益），
  一刀禁掉会让这些场景退化成"永远挂着但内部 if 判断"，反而隐藏了装配关系；而"无主边"是确定的泄漏源。

#### R1i: 包装通道的落地与 band 退役（已确认）
- Status: Confirmed
- Scenario/Trigger: 减伤、免疫、反制这类"改写别人结算"的效果要插入别人的执行。
- Behavior:
  - **`band` / 分段概念退役**：成员内部不再有 `Rewrite`/`Veto`/`Apply` 这类次序枚举。
  - **成员执行＝有序边集合**：自有边（成员所属实体自己声明的，**固定最前**）→ 外来挂载边（按声明序）→ 框架注销边（R1f）。
    不再有独立于边集合的"core"概念——核心逻辑就是自有边。
  - **包装的目标是成员**（包裹该成员的整体执行），不是某一条边；因此不需要"成员＋来源"的二级地址。
  - 相位：`before`（改写输入，LIFO）／`after`（尾部副作用，FIFO）／`replace`（替代整个边集合，最后声明者生效）。
    三者的先后**一律按声明序推出**，不引入优先级数字。
  - **接缝（seam）退役**：需要"在中间插入"就拆成员（R3a 已定）。包装只能包在成员外围。
  - **判定器包装器同属这一套**（相位语义相同，作用对象是判定器而非成员）。
  - **迁移规则**：`injects + band: Rewrite` → `wrap: engine#<成员>, phase: before`（改写视图字段）；
    `Veto` → `before` + `ctx.Stop()`；`Apply` 段的外来注册项 → 外来挂载边。
- Acceptance:
  - [ ] 模型里不存在 `band` 概念
  - [ ] 成员执行序可由"自有边 → 外来边声明序 → 框架边"完整推出
  - [ ] 两个减伤包装器（相邻掩护、海绵装甲）同时生效时，相对次序由声明序推出
  - [ ] 免疫（before + stop）命中后，同成员的 after 包装器与后续边不执行，且行为有明确文档
  - [ ] `samples/` 里 4 处 `Rewrite` 注入迁移后行为等价；另 3 处（1 `Commit`、2 无 `band`）按 R1j 规则迁移
- Terminology: 包装、相位、自有边、外来边、band 退役
- 决策记录: 2026-10-26，父 agent 依 W-20 裁决。判据：band 与包装器在语义上重叠（都是"改变执行次序/内容"），
  R1b 已把"改别人结算"划给包装通道；若保留 band，作者要同时理解"band 值"与"相位"两套次序语言，
  与"更强的抽象"背道而驰。
- **修订（2026-10-26，S13 第一轮证伪"自有边固定最前"）**：
  - 成员声明自己的**自有边位次** `own-edge-position: first | last`（默认 `first`）：
    - `first`＝流程型成员（打出／部署／指向）：自有边（核心流程）先跑，外来扩展续后；
    - `last`＝管道型成员（伤害处理／动作落地）：外来改写先跑，自有边（落地）最后跑。
  - 原因：动作管道的"转发"（旧 `Commit`）与"落地"（旧 `Apply`）都是**链上最后一步**；一律"自有边最前"
    会让外来边与包装永不执行。
  - **`before` 相位改为 FIFO（按声明序正序）**，不再是 LIFO：旧的 `Initiate`／`Announce` 是 priority 升序，
    LIFO 会让减伤叠加的钳制点反转（如"−1"与"封顶 10"的次序）。LIFO 的装饰器嵌套语义在 Orc 里没有真实用例。
  - `after` 保持 FIFO；`replace` 保持"最后声明者生效"。

### R2: targeter 作为特殊判定器
- Status: Confirmed
- Scenario/Trigger: 某逻辑需要玩家在前端做选择（选靶／选位／选牌）。

#### R2a: 现状诊断（代码事实）
- 三条选择路径，只有两条在跑：

  | 路径 | 实现 | 走前端 | 生产使用 |
  | --- | --- | --- | --- |
  | 玩家行动（打出／开发／钳击／调度） | `TargeterManager.RunAsync` | ✅ | ✅ 活跃 |

### R4: 成员 handler 与 owner 回填（已确认：全局函数 + owner 参数）
