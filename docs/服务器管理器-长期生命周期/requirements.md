# Requirements — 多人联机模型重构（管理器-服务器-房间-seat-viewer-controller）

> 状态：**需求已定稿**（R1–R10 全部 `Confirmed`；D1–D5 工程默认值已采纳）。
> 基线依据：`基线调研.md`（同目录）。实现路径见 `implementation.md`（由实现 grill 产出）。

一句话：把 OrC 现在的"一进程＝一服务器＝一房间＝一局＝2 座"竖线，重构为**管理器 → 服务器 → 房间 → seat → (controller, viewer)** 六层模型，并把**管理员**作为正交于 seat 的第三类身份；同时把服务器生命周期从"一场对局"解耦为可由管理器托管的更长生命周期。

**核心模型（一张表）**：权限由"绑不绑 seat"这个拓扑决定，不存在独立的权限档案。

| 角色 | 绑定 seat | 不绑 seat |
|---|---|---|
| **controller**（引擎输入端） | **玩家面**：只能向该 seat 推输入 | **调试面**：直接调引擎内部调试 API |
| **viewer**（引擎输出端） | **该 seat 视角**（脱敏） | **全知**（不经脱敏） |

管理员管的是**这条拓扑本身**（谁能绑、谁不能绑），而不是另一套权限枚举。

## Scope

- Includes：
  - 六层模型的显式对象与归属关系（管理器 / 服务器 / 房间 / seat / controller / viewer）。
  - **管理员**：正交于 seat 的进程主人身份，掌握绑定拓扑、连接许可、房间生命周期。
  - seat 作为"对局设施归属点"与"输入输出转发点"的职责。
  - controller / viewer 的"绑 seat / 不绑 seat"两态及其对应的权限差异。
  - 服务器实例启动前置条件：卡包已注册、双方 lock 并集一致、启动时加载卡牌与卡组。
  - 生命周期长于对局的**服务器管理器**：常驻、多实例托管、四种驱动形态、换进程式热更新。
  - 管理器职责边界：资产注册、依赖分析、资产同步分析。
  - 卡池在服务器存活期内可重装（轮换点生效）。
- Excludes：
  - 引擎内部规则、词条、判定器语义变更（`Orc.Game` 尽量零改动）。
  - 卡牌数值与平衡。
  - 账号 / 匹配 / 排行榜 / 生涯数据。
  - 观战回放（除非 viewer 模型天然覆盖）。
  - WebSocket 承载。
  - 卡组资产化（构筑存档）。
  - 资产的**实际分发/下载**（同步逻辑后做；本轮只做"检出缺口并拒绝开局"）。
  - 管理员远程协议的完整形态（本轮只做进程内管理 API）。

## Constraints

- 既有 2395 项通过的测试是回归底线（当前另有 2 项既有红，见基线调研 §测试基线）。
- 引擎是 1v1（`BattlefieldManager(Players[0], Players[1])`）；seat 数恒为 2。
- 一进程单活跃对局（`MatchExecutor`）；多对局落到多实例（多进程）。
- 资产注册面不可撤销（`AssetRegistry` 无删除 API）；进程级静态面 12 项单向累积。
- 全仓无 `AssemblyLoadContext`；热更新走进程级替换。
- 线上一律字符串协议（自描述 JSON），不传活对象。
- 管理权来源＝进程所有权；线上连接不得自封管理员。
- 权限只由拓扑决定，不得出现"绑了 seat 但仍可调调试 API"或"controller 绑 seat 却收全知输出"的混合态。
- 协议面破坏性变更，不保留 v1 兼容层。

## Requirement Items

### R1: 管理器（Manager）
- Status: Confirmed
- Scenario/Trigger: 操作者（人或 agent）需要在一台机器上持续提供对局能力，而不希望每局重启进程。
- Behavior: 一个**常驻**的管理器，生命周期长于任何单场对局。它**并行托管多个服务器实例**（启动 / 销毁 / 重载），每个实例有稳定标识，独立拥有自己的卡池、房间、端口与运行目录。管理器自身状态（资产库、依赖分析结果、实例清单）在实例更替后保留。
  - 驱动形态：**进程内 API（库形态，可被其他程序携带）／ 独立进程 ／ CLI（bash）／ MCP** 四种入口共用同一套语义。
  - 热更新：**换进程**——销毁旧服务器子进程、用新 dll 起新子进程；管理器不重启。触发＝手动指令为主，可选开启"监视 build 产物自动替换"。
- Acceptance:
  - [ ] 管理器在无对局时持续存活（不因无对局退出）。
  - [ ] 管理器可同时运行 ≥2 个服务器实例，各自独立开局、互不影响。
  - [ ] 管理器可单独销毁/重载某个实例，其余实例不受影响。
  - [ ] 本轮交付**进程内 API** 与 **CLI** 两档驱动形态，二者共用同一套操作语义（同一管理接口，CLI 只是薄适配）。
  - [ ] MCP 面与管理器远程协议同批交付（后续批次）；本轮只要求管理接口已抽出、MCP 可作为其薄适配接入，不在本轮验收内。
  - [ ] 重载某实例后旧进程被彻底回收（无残留子进程、端口可复用）。
  - [ ] 管理员可配置"等待轮换点的超时"；超时后是否强制结束在局对局由配置决定（默认不强制）。
- Terminology: [管理器](../../CONTEXT.md)、[实例标识](../../CONTEXT.md)

### R2: 管理器的资产职责
- Status: Confirmed
- Scenario/Trigger: 任何服务器实例需要加载卡池，或需要判断"双方卡包能否凑成一局"。
- Behavior: 管理器持有**资产库**（进程级、只读、**只增不减**——同 id 多版本并存，进程存活期内不回收）并负责：资产注册、依赖分析、资产同步分析。**运行中的卡池、房间、对局状态不进入管理器**——它们属于各个服务器实例。
- Acceptance:
  - [ ] 管理器能给出一次"资产注册结果"，服务器实例据此加载自己的卡池。
  - [ ] 管理器能给出依赖分析结论（哪些包/资产可用、哪些不可用及原因）。
  - [ ] 管理器能对"两份 lock 声明"给出差异清单（缺哪些资产、哪些版本不一致）。
  - [ ] 管理器不持有任何 `Match` / `Player` / `Room` 活对象。
  - [ ] 多个服务器实例共享同一份资产库，但各自持有独立的运行中卡池。
- Terminology: [资产注册](../../CONTEXT.md)、[依赖分析](../../CONTEXT.md)、[资产同步分析](../../CONTEXT.md)、[资产库](../../CONTEXT.md)

### R3: 服务器实例（Server）
- Status: Confirmed
- Scenario/Trigger: 管理器决定开一台服务器。
- Behavior: 判定分**两个时点**，不得混为一谈：
  - **进程启动**：创建 1 个 lobby 房间、声明 2 个空 seat；只校验"**卡包已完成注册**"（资产库可用/可索引），**不预装任何卡池**。人类 seat 此时没有卡组——卡组由参与者在申请绑定座位时提供；AI seat 可按配置在启动时预置卡组。
  - **房间开局**：校验"**双方各自声明的卡包 lock 并集可用且一致**"（同 id 版本不同＝冲突、任一方缺资产＝缺口），通过后**按并集装配本局卡池**并建局。
  - 玩家提交的卡包为**引用形态**（`{packageId, version, guid}`），与卡组/构筑声明**同一条申请报文**提交；由管理器在资产库中定位与校验，服务器按管理器给出的加载计划装配。
  - **AI seat**：由管理员在启动实例时配置，配置完成即视为"已批准"（不需要再走申请）；其 `packages` 缺省为空集（即只使用人类一侧声明的包，不额外要求）；其卡组若未显式给出，则在**开局装配卡池之后**由该池生成。
  - **并集的参与者按 seat 计，不按连接计**：两个 seat 各自都必须有 controller 与声明（人类经申请、AI 经配置），并集恒为两份声明之并。
  - **沙盒包**作为**实例级固定包**强制加入每局并集（不由玩家声明），保证调试面造出的卡在轮换后仍可用。
  - **沙盒包脚手架由服务器在启动时生成**（幂等），因为沙盒包必须在本局装配前存在；不能等"第一次写卡"才惰性创建。
  - **沙盒包非法时的降级**：开局装配先尝试**剔除沙盒包**重试一次；成功则开局并告警（本次调试产物不可用），仍失败才拒绝开局。避免"沙盒包写坏＝整个实例不可用"。
  - 一场对局终结后，服务器自动轮换出下一个 lobby 房间，服务器进程不退出。**卡池按房间构建**：每局开局前按当时的包集合装配，因此房间轮换天然就是卡池重装点（R9）。
- Acceptance:
  - [ ] 进程启动不因"双方尚未声明卡包/卡组"而失败；启动后存在一个 lobby 房间，其 seat 为空且可申请。
  - [ ] 开局前置不满足时**拒绝开局**（不是拒绝启动），原因可定位到具体包/资产。
  - [ ] 终局后服务器仍存活，并产出一个新的 lobby 房间；旧房间保持 `Ended`。
  - [ ] 合并规则＝**并集**；同一包在双方声明中版本不同＝冲突，拒绝开局。
  - [ ] 任一方缺并集中的资产时拒绝开局，并给出缺口清单（由管理器产出、服务器转达）。
  - [ ] 卡池变更后，新开房间使用变更后的卡池（生效时机见 R9）。
  - [ ] 进程启动时**不装载任何卡池**，因此不存在"启动装错、后续无法卸载"的路径。
- Terminology: [服务器实例](../../CONTEXT.md)、[房间轮换](../../CONTEXT.md)

### R4: 房间（Room）
- Status: Confirmed
- Scenario/Trigger: agent 或玩家在服务器内组织一场对局。
- Behavior: **seat 属于房间**。房间是 seat 的容器，一场对局对应一个房间；**seat 数恒为 2**（与引擎 1v1 一一对应）；seat 随房间创建而创建、随房间终结而失效；终局后房间不可回到房间态。服务器通过**房间轮换**持续提供服务。
- Acceptance:
  - [ ] 房间创建时确定 seat 集合（恰 2 个）；房间终结时其全部 seat 失效。
  - [ ] 跨房间不共享 seat（下一局必须重新入座、重新提供卡组）。
  - [ ] 一个房间只承载一场对局。
  - [ ] 同一服务器实例内同时最多存在一个非终结房间。
  - [ ] seat 索引与 `playerIndex` 一一对应（0↔0、1↔1）。
- Terminology: [房间](../../CONTEXT.md)、[房间态](../../CONTEXT.md)

### R5: seat
- Status: Confirmed
- Scenario/Trigger: 对局需要把"某个参与方"的输入与输出、以及它的私有设施绑定在一起。
- Behavior: seat 的生命周期 ＝ 所属房间的生命周期。**seat 上恰有 1 个 controller（玩家面）＋ 0..N 个 viewer**；对局初始化后的设施（如玩家私有判定器）与 seat 绑定；**seat 是转发点**——把其 controller 推来的输入转给引擎，把引擎输出转给其绑定的 viewer。绑定与解绑由管理员执行（R10）。**seat 绑定是连接级的**：一个连接至多绑一个 seat。
  - **seat 不持有引擎活对象**：它只持 `(对局纪元, playerIndex)`；设施经「当前对局 ＋ playerIndex」解析得到。房间终结使纪元失效，从而保证"设施不再可达"，而无需在 seat 上挂 `Match`/`Player` 引用。
  - **"设施失效"的判定**：纪元不匹配 或 当前无对局 ⇒ 失效。不以"是否被 Dispose"判定。
- Acceptance:
  - [ ] 房间内恰有 2 个 seat；每个 seat 至多 1 个 controller。
  - [ ] 同一 seat 可挂多个 viewer，各自独立断开不影响他人。
  - [ ] 玩家私有设施的生命周期与 seat 一致（房间终结即失效，且不以"仍被引用"的方式可达）。
  - [ ] 轮换时旧持有者被全部停止：AI 驱动、宽限计时、在途选靶（以失败收束）、旧推送队列；不存在"旧持有者作用于新对局"的现象。
  - [ ] controller 断开不影响 viewer 继续接收输出（反之亦然）。
  - [ ] seat 的卡组在房间态声明（每局重新提供）。
  - [ ] 非管理员不得自行把 controller/viewer 绑到 seat。
  - [ ] 座位令牌由管理员批准绑定时签发，并经**该连接自己的**批准响应下发给它（不依赖任何第三方连接转达）；凭令牌重连可恢复原角色与 seat 绑定。
- Terminology: [座位](../../CONTEXT.md)、[对局设施](../../CONTEXT.md)

### R6: controller
- Status: Confirmed
- Scenario/Trigger: 某个参与方要驱动引擎。
- Behavior: controller 是**引擎输入端**，**只负责向 seat 推输入**，不接收输出。按是否绑 seat 分两类：
  - **玩家面（绑 seat）**：绑定到某个 seat（`seat → controller` 至多 1 个）；只能向该 seat 推输入；不能调调试 API；不持有任何"视野"概念。**AI controller 属于玩家面**：同样绑 seat，但由服务器进程内驱动、不走协议；其卡包与卡组声明由管理员代为配置。
  - **调试面（不绑 seat）**：不占 seat；直接调用**引擎内部调试 API**（造卡、`card.load`/`card.write`/`effect.write`、`sandbox.*`、塑造对局等）；走引擎侧协议接入。现有调试判据（回环 ＋ 未绑座 ＋ 写类工具）**完整保留**。
  - **多个调试面 controller 可同时存在**：互不排斥、各自独立接入与断开，任一个的接入/离开不影响其余；不要求独占，也不引入"同一时刻只允许一个编辑者"的限制。
  - **调试面与房间解耦**：房间轮换**不重置**调试面角色（它不绑 seat，与房间无生命周期关系）；其调用的调试 API 作用于**当前房间**的引擎，轮换后自动指向新栈。调试能力分两层——**资产层**（写卡文件、写效果文件：只落磁盘，**无对局要求**）与**对局层**（卡装载进运行中引擎、沙盒塑造：**需活跃对局**）。
  - **第三态 `待许可`（Pending）**：连接已声明角色意图、但管理员尚未批准时，处于此态。**它既不是玩家面也不是调试面**，不具备任何对局或调试能力（只能心跳、取消申请）。此态的存在保证"未绑 seat"不再自动等于调试面，R6 的二分因此没有时间差漏洞。
  - **角色＝申请 ＋ 批准两段**：连接必须显式**申请**角色（不能靠副作用产生）；管理员**批准**后角色才生效。调试面例外——满足现有判据（回环 ＋ 未绑座）时可在申请后立即生效，行为与现状一致。
- Acceptance:
  - [ ] 玩家面 controller 调用调试 API 被拒绝（拒绝原因可读）。
  - [ ] 调试面 controller 不占用 seat，不出现在 seat 快照中。
  - [ ] 调试面 controller 可调用的工具集与现有 `Authoring` + 写类调试工具一致。
  - [ ] 现有调试判据（回环 ＋ 未绑座）行为零变更。
  - [ ] 不存在"既绑 seat 又能调调试 API"的 controller。
  - [ ] 同时存在 ≥2 个调试面 controller 时，各自可独立调用调试 API，互不影响；任一个断开不影响其余。
  - [ ] 处于 `待许可` 的连接既不能提交动作、也不能调调试 API，也不能收到任何推送。
  - [ ] 未绑 seat 的连接**不会**因为没有绑定而自动获得调试能力（须显式申请调试角色并满足现有判据）。
- Terminology: [控制器](../../CONTEXT.md)、[玩家面](../../CONTEXT.md)、[调试面](../../CONTEXT.md)

### R7: viewer
- Status: Confirmed
- Scenario/Trigger: 某个参与方要观察对局输出。
- Behavior: viewer 是**引擎输出端**，**只接收推送，不向引擎输入任何东西**。按是否绑 seat 分两类：
  - **绑 seat**：收到该 seat 视角的脱敏输出。
  - **不绑 seat**：全知输出（可见双方手牌明细）。
  - 视野由"绑不绑 seat"决定，**不是**可配置的档案字段。
  - **角色兼任规则**：一个连接可同时持有 `controller` 与 `viewer` 角色（必须显式申请），但两个角色**共享同一个 seat 绑定**；因此兼任连接上的 viewer 恒为脱敏视角。**全知 viewer 必须是"不含 controller 角色"的独立连接**。
  - **兼任必须在同一次批准中授予**，不接受"先批 controller、再补 viewer"的分次授予。
  - **全知输出的形状**：不新增"与视角无关的视图类型"，也不改 `UiMatchView`/投影提供者。全知帧＝在**同一次投影**中产出**两份座位视角**并打包下发（每份仍是既有 `UiMatchView`），事件段使用**全量版**（不按座位脱敏）。客户端据帧上的视角标识区分"全知帧"与"某座位视角帧"。
  - **全知的合法性只由管理员批准决定**，不受服务器运行模式（play/sandbox）限制。
- Acceptance:
  - [ ] 绑 seat 的 viewer 收到的投影与段不含对手手牌明细。
  - [ ] 不绑 seat 的 viewer 收到全知输出。
  - [ ] 一个 seat 可挂多个 viewer，各自独立断开不影响他人。
  - [ ] viewer 不能提交任何动作（调用动作类工具被拒绝）。
  - [ ] 不存在"绑了 seat 却收到全知输出"的 viewer。
  - [ ] 不存在"同一连接上 controller 绑 seat、viewer 却全知"的组合。
  - [ ] 全知 viewer 在每次状态变化后收到 1 条全知帧（含两份座位视角）＋ 1 条全量段；绑座 viewer 只收到 1 条单视角帧 ＋ 1 条脱敏段。
  - [ ] 在 play 模式下，经管理员批准的全知 viewer 能正常收到输出（不再被运行模式拒绝）。
- Terminology: [查看者](../../CONTEXT.md)、[视角](../../CONTEXT.md)、[全知](../../CONTEXT.md)

### R8: 协议面与迁移
- Status: Confirmed
- Scenario/Trigger: 重构落地。
- Behavior: **协议面破坏性重构，不保留 v1 兼容层**。客户端（`Orc.Client`）、MCP 桥（`Orc.Mcp.Bridge`）、控制脚本（`sandbox-server-ctl.py` / `start-sandbox-server.bat`）、工具脚本与既有测试同步改造为新模型。
- Acceptance:
  - [ ] 新协议面不包含任何 v1 兼容分支或翻译层。
  - [ ] 受影响的现役入口全部有对应的新用法（客户端、桥、脚本、Agent 操作手册）。
  - [ ] 全量测试 0 新增失败（允许按新模型重写既有测试，但不得留下跳过/禁用）。
- Terminology: —

### R9: 卡池重装（资产可变）
- Status: Confirmed
- Scenario/Trigger: 服务器实例存活期内，卡包目录内容发生变化（新增/修改/删除包）。
- Behavior: 服务器能够用变更后的卡包重新装配卡池，且不影响服务器进程存活；**卡池按房间构建**——每局开局前按当时的包集合装配，因此**房间轮换天然就是重装点**，不需要"待生效队列"。**"整套服务栈"的范围**＝房间级对象（服务层门面、对局执行器、房间控制面、工具表）＋ 对局；**进程级对象（传输宿主、串行执行队列、会话）不重建**，跨房间长存。变更失败时用**最后一次成功的包集合**回退重试一次，仍失败则拒绝开局。
- Acceptance:
  - [ ] 变更后无需重启服务器进程即可生效。
  - [ ] 变更失败（如 lock 冲突）时，服务器保持原有可用卡池，不进入半装载态。
  - [ ] 变更结果可观测（哪些包/资产被重装、哪些失败及原因）。
  - [ ] 有活跃对局时提交变更，在该局终结后的轮换点应用。
  - [ ] 轮换期间进程级对象（传输宿主、串行队列、既有连接）不重建；连接保持存活。
- Terminology: [卡池重装](../../CONTEXT.md)

### R10: 管理员（Administrator）
- Status: Confirmed
- Scenario/Trigger: 服务器进程实例被启动，需要有主体来支配这台服务器在**对局之外**的状态与生命周期。
- Behavior: **服务器启动者即管理员，正交于 seat**（不占 seat、不出现在 seat 快照中）。管理权来源＝**进程所有权**——谁持有进程实例的控制权，谁就有权直接调用其管理 API，不引入额外鉴权层。
  - **管理面 ≠ 引擎调试面**：管理员管"对局外服务器的状态与生命周期"；引擎内部调试 API 归调试面 controller（R6），两者不重叠。
  - 管理 API 覆盖：**绑定拓扑**（把 controller/viewer 绑到 seat 或解绑——授予/收回权限的唯一手段）、**连接许可**（决定哪些连接被允许接入、可撤销）、**房间生命周期**（开局/终止/轮换）、**卡池重装**（R9）、**服务器启停**。
  - **本轮承载**：管理 API **实现在服务器进程内**；管理器作为该进程的创建者（即「进程主人」），经**父子私有通道**调用它。该通道不监听端口、仅创建者可写、生命周期与子进程绑定，因此**属于进程内范畴，不构成"远程"**。远程管理协议（供第三方 agent 使用）接在管理器上，后续批次实现。
  - **能力开关属于实例配置**：`AllowDebugWrites`、沙盒写根等决定"这台服务器能做什么"的开关，由管理员在**启动实例时**声明（spawn 参数），不通过 CLI 隐式传递。
  - **沙盒包重置**：管理员可执行"重置沙盒包"（删除并重建脚手架），用于从"沙盒包被写坏"恢复，无需重启服务器进程。
  - **执行上下文**：管理操作与引擎动作**共用同一串行执行队列**——凡改动引擎、房间/seat、卡池或开局装配输入的（开局、终止、绑定/解绑、撤销许可、沙盒重置）都在队列内执行；纯只读查询在队列外。
  - **"远程可调"判定口径**：需要①网络可达 且 ②调用者非进程主人，二者同时成立才算远程。父子私有通道两条都不满足。
- Acceptance:
  - [ ] 管理员不占用任何 seat，其存在不改变房间的 seat 数。
  - [ ] 管理员可执行 seat 绑定/解绑；绑定即授予对应权限，解绑即收回。
  - [ ] 管理员可决定某个 controller/viewer 连接是否被许可，并可撤销已许可连接。
  - [ ] 管理员可列出当前处于 `待许可` 的连接，并按连接标识予以批准或拒绝。
  - [ ] 管理面不暴露任何引擎调试 API；调试面不暴露任何管理能力。
  - [ ] 管理 API 不依赖 seat 令牌；线上连接不得自封管理员。
  - [ ] 管理 API 与调试面的鉴权判据互不复用。
  - [ ] 本轮不存在任何"远程可调"的管理入口（口径见 Behavior；父子私有通道不算远程）。
- Terminology: [管理员](../../CONTEXT.md)、[连接许可](../../CONTEXT.md)、[进程主人](../../CONTEXT.md)、[管理面](../../CONTEXT.md)

### R11: 连接中断与对局终止
- Status: Confirmed
- Scenario/Trigger: 对局进行中某个 controller 断线；或管理员主动终止对局。
- Behavior:
  - **房间态断线**：立即释放该 seat 的绑定（与现状一致）。
  - **对局态断线**：绑定**保留**，进入宽限；宽限**只在轮到该 seat 时计时**（避免对手还没打完就被判胜）。宽限到期仍未回 ⇒ 服务器代该 seat 认输，对局结束。
  - **局中不允许换人**：只允许**原 controller 凭令牌重连**恢复；换人必须走"终止 → 轮换 → 新人申请"。
  - **断线期间 viewer 不受影响**：绑座 viewer 继续收该 seat 视角推送，全知 viewer 继续收全知输出；controller 的重连/判负只影响动作面。
  - **管理员主动终止**：对局结束且**无胜者**（终局原因＝`Aborted`），并记录终止由管理员发起。
  - **管理员撤销许可 ≠ 意外断线**：撤销 **controller** 立即生效、**不给宽限**——对局中等于该 seat 认输并结束对局，房间态则直接释放绑定；撤销 **viewer** 只断开该 viewer，不影响对局。两者都不是"断线"，不进入宽限计时。
- Acceptance:
  - [ ] 房间态 controller 断线后绑定立即释放，seat 可被重新申请。
  - [ ] 对局态 controller 断线后绑定保留，且宽限仅在轮到该 seat 时推进。
  - [ ] 宽限到期后服务器代该 seat 认输，对局正常终结。
  - [ ] 局中第三方无法接管该 seat（只能原 controller 凭令牌重连）。
  - [ ] controller 断线期间，该 seat 的 viewer 仍持续收到推送。
  - [ ] 管理员终止后对局状态为已结束、胜者为空、终局原因为 `Aborted`。
- Terminology: [宽限期](../../CONTEXT.md)、[终止](../../CONTEXT.md)

### R12: 房间态的信息可见性
- Status: Confirmed
- Scenario/Trigger: 房间尚未开局时，连接需要了解座位状态；或座位状态发生变化。
- Behavior:
  - **`room.info` 对所有连接可调**（含 `Connected` / `Pending`）：未申请座位的人必须先能看到"哪些座位空着"，否则无法决定申请哪个。
  - **快照按角色裁剪**，房间态同样是「视角」：
    - 公开：seat 索引、是否被占用、座位状态（空闲/待许可/已批准/已断开）、`displayName`。
    - 私密：**自己的**卡组与卡包声明。
    - **对手的卡组与卡包声明永远不可见**——包括全知 viewer（全知是对局输出，不是构筑隐私）。
    - 调试面与管理员可见全量。
  - **座位状态变化经 `notify/room.seats` 推送**（极简事件，只含 seat 索引与状态，不含卡组/卡包），不恢复整份房间快照的推送。
- Acceptance:
  - [ ] 刚完成 `initialize`、尚未申请座位的连接可成功调用 `room.info`。
  - [ ] 任一角色都无法读到对手的卡组与卡包声明（全知 viewer 亦不可）。
  - [ ] 调试面可读到全量声明。
  - [ ] 座位被占用/批准/断开时，相关连接收到 `notify/room.seats`。
  - [ ] `notify/room.seats` 载荷中不含任何卡组或卡包字段。
- Terminology: [房间态](../../CONTEXT.md)、[视角](../../CONTEXT.md)
