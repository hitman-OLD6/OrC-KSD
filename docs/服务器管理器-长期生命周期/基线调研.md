# 基线调研：多人联机模型重构（管理器-服务器-房间-seat-viewer-controller）

> 调研日期：2026-10-21　范围：`src/Orc`、`Orc.Game`、`Orc.Mcp`、`Orc.Server`、`Orc.Packages`、`Orc.Protocol`、`Orc.Client`、`Orc.Mcp.Bridge`、`docs/多人支持-服务端客户端分离/`
> 本轮**只读**，未改任何产品代码。
> 实测基线：`dotnet build OrcEngine.sln` → **0 错误 / 6 警告**（CS8622×1、CS8620×3、CS8619×1、xUnit2013×1，均为既有代码）；全量测试见文末。

---

## 0. 一句话结论

现状是**一条竖线**：一个进程 ＝ 一个服务器 ＝ 一个房间 ＝ 一场对局 ＝ 恰好 2 个座位。

而"座位"在代码里**不是一个对象**——它只是 `int seat`（0/1）这个索引，加一个可空的 `ClientSession.Seat` 字段。用户要的六层模型里，**只有"房间"和"控制器"有对应类型**；`seat`、`controller`、`viewer` 三者全部坍缩在 `ServerHost.ClientSession` 这一个私有类里（它既读请求又收推送）。

因此这次重构的主战场不是"加功能"，而是**把 `ClientSession` 拆成三个显式概念**（seat / controller / viewer），并把"对局设施"的归属从 `Match.Players[i]` 上移到 seat。

## 3. 六条硬约束（决定重构边界，不可绕过）

### 3.1 引擎是 1v1，不是 N 人
```csharp
_battlefieldManager = new BattlefieldManager(_playerManager.Players[0], _playerManager.Players[1]);  // Match.cs:529
var enemy = match.Players[1 - seat];                                                                   // McpService.Projection.cs:119
```
"服务器声明多个 seat"与"引擎支持多玩家"是两件事。当前 `seatIndex ↔ playerIndex` 一一对应且只有 0/1；任何"N seat"设计都必须先回答"N>2 时对局怎么开"。

### 3.2 一个进程只有一个活跃对局
`MatchExecutor` 持 `_match` 单字段，`CreateMatchAsync` 开头 `if (Executor.HasMatch) return Failed("已存在活跃对局")`（`McpService.MatchLaunch.cs:34`）。`Attach` 冲突即抛（`MatchExecutor`）。"管理器下自建多个房间/对局"在**同一进程内**不可达，除非一房间一服务器进程。

### 3.3 输入与输出共用一个会话对象
`ClientSession` 同时持有：入站读循环、出站有界 Channel、`Seat?`。这带来两个后果：
- 无法"一个人操作、多个人观看"（旁观者没有 seat 就收不到任何 push）；
- 无法"AI controller + 人类 viewer"（AI 不走协议，viewer 只能靠 `session.Seat`）。

### 3.4 资产注册不可撤销，静态面单向累积
- `AssetRegistry` **全类无 Remove/Unregister/Clear**（`AssetRegistry.cs:93-269`）；
- `EngineHost.Assets` 是 `readonly`，卸载包只改 `Catalog` 不动 `Assets`（`EngineHost.cs:363`、`:461`）；
- `KeywordRegistry` 运行期不开放注销（`KeywordRegistry.cs:116-118`）；`CardPackKeywordLoader.KeywordOwner` 是静态且 `Unloaded` 直接 return（`CardPackKeywordLoader.cs:13-22`）；
- 只有 `CardComponentRegistry.Unregister` 可逆，但需自行遍历、无事务（`CardComponentRegistry.cs:106-123`）。

### 3.5 零程序集热加载
全仓 `AssemblyLoadContext` / `Assembly.LoadFrom` / `LoadFromAssemblyPath` **零命中**。当前"热更新"的唯一形态是：改源码 → `dotnet build src/Orc.Server/Orc.Server.csproj`（必须构建 Server 才会刷新其 bin 下的依赖副本）→ 重启进程。

### 3.6 进程生命周期 ＝ 对局生命周期
`--exit-on-end` 为无头默认；`Program.Main` 等待 `host.Headless?.Stopped`（`Program.cs:74-75`）；`HeadlessContext.MaybeFinalizeAsync` 在终局写 summary 后 `RequestStop(0)`（`HeadlessContext.cs:457-460`）。`ServerProcess` 还会自动加 `--parent-pid`，父进程一死服务端跟着退出（`ServerProcess.cs:88-93`）。

## 4. 权限模型现状：所谓"两类"到底是哪两类

代码里存在**三套并行、互不对齐**的分类，你说的"controller/viewer 各分两类"目前**没有**对应实现：

| 层 | 分类 | 取值 | 作用点 | 证据 |
|---|---|---|---|---|
| A. 传输层（工具级） | `SeatScope` | `Bind` / `OwnerScoped` / `SeatRequired` / `Agnostic` / `OrchestratorOnly`（**五类**） | `ServerHost.Gate` 逐工具校验 | `SeatScopeRegistry.cs:12-31`、`:583-637` |
| B. 服务层（模式级） | `McpServiceMode` | `Player` / `Authoring`（**两类**） | 决定工具是否登记（`sandboxOnly`）与观察面分支 | `McpServiceOptions.cs:6-13`、`McpService.AddTool:102-111`、`ObserveTools.View` |
| C. 房间层（控制器来源） | `ControllerKinds` | `local` / `remote` / `ai`（**三类**） | 房主判定、AI 驱动、`kind:"local"` 仅回环 | `RoomContracts.cs:19-29`、`ServerHost.GateBind:642-662` |

**输出面的"两类"只以分支形式存在**，没有模型：
| 输出 | 分支条件 | 可见性 | 证据 |
|---|---|---|---|
| `notify/view` | 会话有 `Seat` | 按座位脱敏投影（`ProjectView(seat)`） | `ServerHost.cs:986-1007` |
| `notify/segment` | 会话有 `Seat` | 按座位脱敏段（`MatchEventVisibility` + `match.Players[seat]`） | `ServerHost.cs:1036-1059` |
| `observe.view`（摘要） | `Mode==Authoring` 且未绑座 | **全知**（含双方手牌 `hand`） | `ObserveTools.View:142-190` |
| `observe.view {panel:true}` | 任意 | 投影面板（需 seat） | `ObserveTools.cs` + `McpService.Projection.cs:26` |

> **需要你确认的"两类"**：是 (a) `SeatScope` 里的 `OwnerScoped` / `SeatRequired`？(b) `McpServiceMode.Player` / `Authoring`？(c) `ControllerKinds` 的"房主 / 非房主"？还是 (d) 一种尚未存在的、你心里的分类（比如 controller = 玩家 / 编排者，viewer = 玩家视角 / 上帝视角）？这决定新模型的类型设计。

## 5. 资产 / 依赖 / 同步能力现状

### 5.1 两条互不相交的装载链
| 链路 | 入口 | 产出 | 写 `AssetRegistry` | 产出 `LoadList` |
|---|---|---|---|---|
| A 宿主装载 | `EngineHost.FromDiscovery` | `AssetCatalog` / `Snapshot` | 否（只写插件服务资产） | 否 |
| B 建局装载 | `MatchCardAssembly.Register(dirs)` | 新 `AssetRegistry` + `AssetIdBridge` + `AssetLoadPlan` | **是（每次新建）** | 是 |

`MatchCardAssembly.Register` **每次调用都新建注册表**（`MatchCardAssembly.cs:116-117`），所以它对自身幂等，但**无增量能力**；`Attach` 只能成功一次，失败后该实例不可复用（`:195-211`）。服务端在 `ServerBootstrap` 与每局 `CreateMatchAsync` 各调一次——**同一份卡包被完整解析两遍**。

### 5.2 依赖只在资产级；包级依赖是死的
- `manifest.requires`：**纯声明**，不参与解析、不进 lock、不驱动装载顺序（`PackageManifest.cs:68-71`）；
- `manifest.dependsOn`（包级）：已退役，读时忽略并告警（`:352-381`）；
- 真正生效的是 sidecar 的资产级 `dependsOn`，由 `LoadListPlanner.Plan` 消费（`LoadListPlanner.cs:159-197`）。

### 5.3 合并冲突是 fatal，没有"降级到共同子集"
`LockConflict` / `DuplicateLockEntry` / `DeclaredConflict` / `Cycle` 均 `IsFatal`（`LoadListPlanner.cs:67-70`）→ `AssetLoadPlan.IsValid=false` → `MatchCardAssembly` 直接抛（`:166-171`）。**这正是"双方 lock 不一致就开不了局"的现状形态**，但它没有"告诉双方差在哪、该怎么同步"的产出。

### 5.4 没有"两侧比对"的 API
- 唯一跨进程对账：`ServerBootstrap.ComputePackFingerprint(dirs)` 对**整个目录全部文件**做 SHA-256 取前 16 位（`ServerBootstrap.cs:126-156`）——只回答"是否同一份"，**不产出差异条目**；
- 最接近的积木：`LoadList.FirstChangedLayer(previous)`（首个差异层号）、`AssetLoader.Deltas`（同实例内 Reloaded/Retired）、`PluginAssetLockVerifier.Verify`（仅插件服务资产的四元组比对）。
- **缺**：能表达"A 有 B 无 / 版本不同 / 内容不同"的条目模型，以及"包级需同步清单"。

### 5.5 进程级静态面（会跨对局存活，共 12 项）
| 状态 | 位置 | 可重置 |
|---|---|---|
| `KeywordRegistry.Factories/Order/BattleKeywords` | `Cards/KeywordRegistry.cs:31-33` | 部分（运行期不开放注销） |
| `KeywordRegistry.EffectBindings` | `:34` | 替换式，无清空 |
| `CardComponentRegistry` | `Cards/Data/CardComponentRegistry.cs:48-49` | 可 `Unregister`，无 `Clear` |
| `CardPackKeywordLoader.KeywordOwner` | `Orc.UI/CardPackKeywordLoader.cs:13` | **否**（`Unloaded` 直接 return） |
| `BuiltInPlugin._processRegistered` | `Orc.Plugins.BuiltIn/BuiltInPlugin.cs:182` | 否（一次性闩锁） |
| `CardTextEffectCompiler.Ops` | `EffectParsing/CardTextEffectCompiler.cs:53-70` | 否 |
| `CardValiditySuite.BuiltIn` | `Cards/Loading/CardValiditySuite.cs:34` | 否 |
| `EngineHost.Assets` | `EngineHost.cs:363` | **否**（无删除 API） |
| `AssetRegistry.CardLoaders` | `AssetRegistry.cs:104` | 否（无 Unregister） |
| `AssetRegistry._runtimeCards` | `:98`、`:256` | 否（只追加） |
| `PackageLifecycleNotifier._observers` | `PackageLifecycle.cs:48` | 否 |
| `EngineHost._failures/_warnings` | `:143-144` | 否 |

> **对管理器的直接含义**：想在"一个进程内换一套卡包再开一局"，要么绕开这 12 项（做不到），要么**一进程一服务器**（当前形态），要么引入隔离边界（新 AppDomain 不存在 → 只能新进程）。

### 5.6 指纹不覆盖源文件
`PackageVersion.ComputeContent` 只哈希 **sidecar**（`PackageVersion.cs:75-121`），`ComputeLayout` 只哈希 sidecar **路径**（`:42-58`）。改卡数据体但不动 sidecar ⇒ 包版本不变。所以"lock 一致"**不等于**"卡包内容一致"；对账要额外比源文件（现在只有 `ComputePackFingerprint` 这么做）。

## 6. 生命周期管理现状：管理器要接替的三套东西

| 入口 | 形态 | 能力 | 缺口 |
|---|---|---|---|
| `Orc.Client.ServerProcess` | 进程内 C# API | 启动、读就绪行、stderr 落盘、`Kill(entireProcessTree)`、自动带 `--parent-pid` | 无资产注册、无 lock 对账、无多实例编排、无热更、**父进程死则服务端死** |
| `sandbox-server-ctl.py` | bash/python | `start/stop/status/restart`、`--check` 四项自检、detach、端口探测、pid 文件 | 同上；且 detach 在 Job Object 内会被回收 |
| `start-sandbox-server.bat` | 双击脚本 | 前台常驻、参数固定对齐 `mcp.json` | 无编排能力 |

三者共同的根因：**服务器进程自己解析"用什么卡包"**（`--packs`）。管理器要做的第一件事就是把这件事从服务器手里拿走。

## 8. 待你拍板的 8 个问题

> 按你的习惯直接文字作答即可，不必用选项。

**Q1「多个 seat」的上限与含义**
服务器可声明 N 个 seat，但引擎是 1v1。是指：(a) 声明 N 个、一场对局只激活其中 2 个；(b) 声明 N 个、一个 seat 可坐多人（队伍）；(c) 未来要支持 >2 人真多人对局（需改引擎）；(d) 就是"2 个 seat 更明确地建模"？

**Q2 房间与服务器的基数**
一个服务器进程内：(a) 1 个房间（现状，仅重命名）；(b) 1 个服务器 = 1 个"对局容器"，房间是对局的逻辑分组；(c) N 个房间（需要多 `Match` 实例，与 3.2 冲突，代价大）？你提到"agent 在管理器下自建房间和对局"，这句话里"房间"和"对局"是同一个东西还是两层？

**Q3 controller 的两类权限，具体是哪两类？**
见 §4 的四个候选 (a)(b)(c)(d)。同时请说明这两类**决定什么**：能调哪些工具？能改对局还是只能改资产？还是"能否越位操作别人的 seat"？

**Q4 viewer 的权限分类**
我理解至少要有"玩家视角（脱敏）/ 上帝视角（全知）"两类；是否还需要第三类"摘要/统计视角"（现在的 `observe.view` 摘要面）？viewer 是否需要 token（独立于 seat token）？

**Q5 "seat 转发 controller 输出"的语义**
是指：(a) seat 做**协议转译**（controller 说的话 → 引擎调用）；(b) seat 做**权限裁决**（controller 想做的事先经 seat 校验）；(c) seat 做**串行化/排队**（同一 seat 的多个 controller 输出排队）；(d) 以上全部？现在 (a) 由 `ServerHost.HandleToolsCallAsync` 做，(b) 由 `Gate` 做，(c) 由 `SerialWorkQueue` 做——需要确认新模型是"搬家"还是"加一层"。

**Q6 管理器与服务器的进程关系**
(a) 管理器**独立进程**，通过 stdio/TCP 管 N 个服务器进程；(b) 管理器是**库**，被宿主（WorkBuddy / Godot / CLI）进程内引用，服务器仍是子进程；(c) 管理器与服务器同进程（则受 §3.2/§5.5 限制，只能一进程一局）？你倾向哪种？"携带管理器的其他程序"听起来像 (b)。

**Q7 热更新的粒度**
(a) **进程级替换**（管理器 kill 旧进程 → 起新进程），实现简单、可靠，但丢对局状态；(b) **程序集级重载**（`AssemblyLoadContext` 卸载/重载 `Orc.Game`/`Orc.Mcp`），需解决静态面（§5.5 的 12 项）、`Timer`/线程/句柄泄漏、跨 ALC 类型身份问题，工作量大且脆弱；(c) **只换资产不换 dll**（现有 `EngineHost.TryReloadCardPack` 已部分支持）。你期望的是 (a) 就够，还是必须 (b)？如果是 (b)，是否只要求"管理器自身不重启、服务器进程可可换"？

**Q8 "双方合并后的加载 lock 一致"的双方是谁**
(a) 两个 seat 的玩家各自携带一组卡包/lock；(b) 服务器与管理器各持一份；(c) 服务器 A 与服务器 B（联机对局的两端）？以及"不一致需要同步"的同步方向：以谁为准？（这决定管理器需要产出什么：差异清单 / 可合并子集 / 强制覆盖计划）
