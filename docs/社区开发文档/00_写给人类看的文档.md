# Orc-kards 引擎DIY指南入口



本文本大致描述了整个orc引擎diy的概述，主要是让DIYer可以快速地了解orc引擎的DIY支持，了解orc引擎DIY的原理，了解DIY的设计思路，以及简单地开始DIY，本质是教程。理论上随着游戏/引擎的更新，这个文档会同步更新，记录最新的DIY支持

本文主要是指导基于代码和文本进行DIYd的路径，主要是因为游戏内置的图形化的效果编辑器(就是那个让你填什么触发时机，条件和动作的)和效果原语推断(让你输入一个框来自动生成效果)截止26/10/25还不稳定，目前游戏内DIY只有直接生成卡包资产这一条路，同时，这条路也是表达力最强(什么DIY都能做)，上限最高，且实际上对于有编程基础的人而言更简单的路径

虽然是教程，但是由于orc引擎设计极其繁琐(为了绝对的效果表达力，这是很有必要的)，实际上由人类完整手写卡牌和效果是非常难的，由此，实际上我们只推荐使用ai agent来编写卡包。我们为agent提供了完整的文档系统，完备的资产管理工具和调试工具，而后两者仅能由agent使用。在这种情况下，使用agent进行DIY(即，你给agent描述或者卡图，agent直接生成可玩的资产)是最推荐的路径



接下来，我们将描述orc的核心原理



### orc说明书



orc引擎本质上是一个编排引擎，即"告诉程序什么时候该被执行"的一个编排工具，和命令式的代码不同，我们允许任何逻辑自由声明其运行的位置，并且，"声明一段逻辑运行的位置"本身也是逻辑。对于kards这种，新机制可以变更旧机制的运行顺序，甚至是直接中断(我们称这种改变效果的效果为"元效果")的游戏，引入逻辑编排可以允许中断，修改和分支任何已有逻辑

对于orc引擎的运行，可以想象一个树：一个树只有一个起点，称为触发器，每个触发器本身不携带逻辑，只描述"本树关心什么参数，以及运行时会使用哪些数据"。触发器上面可以挂载handler(可以称为处理器，但是我们习惯称为handler)，hander就是一段独立的逻辑，这段逻辑本身可以执行任何事情，比如造成伤害，抽牌，加入/移除单位，甚至直接判定输赢。handler可以挂在触发器上，并且声明其优先级(触发器本身本身声明多个优先级区段，不同区段之间隔离，handler要声明区段和优先度)。当一个触发器被触发时，触发器会先判定是否合法(此处仅为兜底，实际上让触发器来判定合法是不符合规范的，因为触发器不能处理错误)，然后对参数进行包装，划定变量，可编辑范围等，之后交由各个handler按优先级处理。关键是，一个handler可能在内部触发了其他的触发器，此时，引擎会深度优先执行(即不管之前的树，先把新的树执行完，永远是这样，不管多少层)，由此，一个逻辑的执行逻辑就类似一颗树，从一个根触发器开始，按顺序执行所有分支(即handler)，然后每个handler可能是其他树的根触发器。orc引擎本质就是维护这些触发器和handler的加载/注册/注销的管理器，而orc-kards的游戏层本质就是几十几百个触发器和它们的handler

也就是说，写效果逻辑本身是很简单的，就是.csx脚本(真的很简单，只要你高中的python课稍微听一点，再看一点示例，很容易理解)，并且上限很高，什么遍历(就是"每有一个XXX")，循环，分支什么的都是非常容易写的，但是，什么时候挂载handler，什么时候注销，卡牌的效果如何从csx文本变为游戏内的效果，这些编排方面的才是主要的难点

举个例子，对于"无心漫谈"这张德国一费反制而言，"对一个单位造成三点伤害"是很容易写的，就是找到合适的触发器，然后传入合适的参数，这放在handler里不超过两行代码，但是，需要让这个handler在合适的时机运行，就比较复杂了。首先，反制卡的效果需要加载，这要求效果自己声明一个"主触发器"，即本效果的初始化逻辑，以及主触发器的挂载点位(一个触发器的名字)，当加载这个卡牌效果时，引擎会读取并加载主触发器(本质是加载handler)，然后把效果的主触发器挂载在效果声明的挂载点位上面，而主触发器也不是直接的效果，它只是初始化效果，它需要向反制卡牌自带的触发器(本卡被激活的触发器)再注入一个handler(实际上是两个，还有一个"取消激活时的逻辑"，用来取消挂载，不过我们要求挂载触发器时必须声明保底的注销点，即使不专门写第二个handler来注销，引擎也能保证不泄露)，这个handler会在反制被激活时被运行，而这个handler的效果也不是真正的效果，它是"反制被激活时的效果"，实际作用是，向部署卡牌的触发器挂载一个handler(这个handler需要在单位的"单位化"，即上桌变为单位之后运行)，这个被挂载的handler才是那个"造成3点伤害"的handler。所以，无心漫谈的效果，翻译为人话应该是三层嵌套
