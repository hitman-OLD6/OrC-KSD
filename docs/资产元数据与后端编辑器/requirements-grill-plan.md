## 已对齐决策

- **D1（Q1=a）**：**统一 sidecar**——每个资产源文件（`*.card.json` / `*.prefab.json` / `*.csx` / 其他 json）配一份元数据文件，内含该文件声明的**全部资产条目**（卡牌/效果/触发器/handler）。理由（用户）：方便统一管理。
  - 推论：卡牌也走 sidecar，原句"卡牌的元数据存在卡牌就存在"须以**成对/宿主语义**落地（Q1d）。
- **D2（Q1a=b）**：GUID **随版本重新派生**（含包/插件 ID ＋ 版本 ＋ 资产种类 ＋ 局部 ID）。即 GUID 是**版本级身份**，不是跨版本资产身份。
  - 补充（用户）：允许**多版本同时注册**，但**同一次加载只能加载一个**。
- **D3（Q1b=b）**：GUID 与既有锚点**并存**——`card.id` / 触发器 `stableKey` / 事件 `id` 保留为文件内锚点，元数据记录"GUID ↔ 局部锚点"映射。
- **D4（Q1c=b）**：资产名**改分型**——类型名从加载方（json/csx/asm）改为资产**种类**（card/effect/trigger/handler），形如 `card：rifleman@<guid8>#1.2.3`；**内含资产版本继承宿主文件版本**。
- **D5（Q1d=a）**：sidecar 采用**宿主语义**——meta 为元数据唯一载体；宿主源文件缺失 ⇒ 该 meta 不成立（孤儿 meta 进报告、不注册）；卡在 meta 缺 ⇒ 该卡按"无元数据"走三档判定。
- **D6（Q1e=a）**：依赖**声明**用「局部 ID ＋ 版本约束」，lock 用 GUID **固化**。lock 表达"卡包的**正式版**"；加载时**只加载 lock 里的版本**；lock **只能手动更新**（编辑器内由编辑者决定），资产改动与"纳入正式版"解耦。
  - 被改资产的版本号**必须递增**；旧版删不删由编辑者定夺。
  - 卡包降级为资产的**目录/容器**：只负责**硬 GUID 冲突**检测；加载/依赖/冲突的严格语义全部由 lock 承担。
- **D7（Q1f=a）**：保留历史版本条目。加载 match 时：先**合并**参与方的 lock；若 lock 间存在"同一资产的不同版本"＝**报错**；否则合并结果即为本次加载的版本集合，从**已注册资产**中按**依赖顺序**加载。
- **D8（术语，待用户确认）**：**资产（asset）**＝跨版本实体（包 ID＋种类＋局部 ID）；**资产版本（asset version）**＝GUID 标识的具体一份。二者不可混用。
- **D9（Q7a=a）**：lock 为**包根两文件**（本包正式版资产 GUID ／ 依赖资产 GUID），随包分发。冲突键沿用 D8 的资产身份（含包 ID）。
- **D10（Q7b）**：**注册 ≠ 加载**：
  - **注册**＝元数据的加载：解析元数据 ＋ 生成包内**全部资产的 DTO 类**（不实例化、不进对局）。
  - **加载**＝给定额包集合，**合并其 lock** 得到"本次要加载的资产"集合，在**已注册资产**上做**拓扑分层**（第 0 层＝无依赖，第 N 层＝只依赖 ≤N-1 层），产出**二维层状加载列表**；依赖检测、拓扑排序、加载顺序在同一次计算中完成；资产加载器按该列表逐层装载，装载完成即可玩对局。
- **D11（Q7c=a）**：编辑器产出**测试 lock**（版本只递增，可引用已有资产）；沙盒对局提供**重新加载**方法；编辑器要加载新资产时，把测试 lock **合并进加载列表**后重新加载。
- **D12（Q7d=a）**：删除旧版仅告警不阻止。理由（用户）：社区卡包可能在**不同设备离线开发**，跨设备引用管不了；只保证 **lock 内版本可运行**，且**同一卡包不同版本的 lock 不同时混用依赖**。
- **D13（加载列表缓存与增量重载）**：加载逻辑缓存二维列表。给定新列表时，从第 0 层向下扫描，定位**第一个发生变更的层**，从该层起**重新加载其后的全部资产**（之前的层不动）。
- **D14（测试 lock 形态）**：测试 lock 与正式 lock **并存且互不合并**。
- **D15（Q15=a）**：资产加载器原生支持**测试资产**：
  - 所有测试 lock 合并为**测试加载列表**；加载器先加载**正式加载列表**，再加载**测试加载列表**。
  - **正式 lock 只与正式 lock 合并；测试 lock 只与测试 lock 合并**；冲突判定各自域内生效。
  - 测试资产 ID 加**测试前缀**；依赖**单向**：测试资产只能依赖正式资产（及测试资产之间互依赖），正式资产不得依赖测试资产。
- **D16（Q16.1=b）**：层内顺序按**局部 ID 字典序**（同时用户又说"不考虑层内顺序、先到先得"——见 C20 待仲裁）。
- **D17（Q16.2=a）**：内含资产（触发器/handler）**随宿主同层装载**，不作为独立拓扑节点。
- **D18（Q16.3）**：**禁止环形依赖**（报错并输出环路径）；拓扑用 Kahn 算法（层间有序）。
- **D19（Q17=a）**：增量重载**只刷新资产注册面**，不破坏对局稳定性（已实例化的卡不受影响）；是否允许重载由**判定器门禁**裁决（例：是否正在等待 targeter）；失败**全有或全无**。
- **D20（Q18=a）**：测试资产与正式资产**同应用层 ID 遮蔽**；新增**中间层**负责"**应用层 ID 引用 → 资产层 ID 引用**"的转接（遮蔽表在此层生效，测试段覆盖正式段同名映射）。
- **D21（Q19=a）**：层内按**局部 ID 字典序**排序；但**加载执行不承诺层内语义顺序**（排序用于文档/确定性展示与增量比对，不承载语义）。
- **D22（Q20 同意）**：重载门禁＝**单一判定器** `reloadGate`（返回"允许＋原因"）；门禁清单归一；被拒返回**结构化结果、不抛错**；沿用判定器机制**可被 wrapper 改写**。
- **D23（Q21 同意）**：正式列表失败 ⇒ **不尝试**测试列表；测试列表失败 ⇒ **只回滚测试段**；测试资产依赖的正式资产不在正式 lock 中 ⇒ 该测试资产判**非法**（进报告、不加载），不整段失败。
- **D24（Q2a）**：**包版本＝hash(包 ID ＋ 包内元数据 ＋ 时间戳)**，**自动生成**（仅包 ID 可编辑）；用途＝区分不同开发者产出的同 ID 包，防止混用。**包版本不参与依赖**——依赖只由资产自身满足。
- **D25（Q2b）**：包版本可附加 `tmp` 表示草稿。**资产版本**＝纯数字 1..8 段（`.` 分隔、每段 ≤ int32），自动生成、可手写。
- **D26（Q2c）**：版本比较＝**左对齐、缺段补 0、逐段比较、第一处不等决定大小**；递增＝**严格大于**旧版（允许增段、禁止降级与相等）；默认自动递增＝**尾段＋1**；GUID 派生用**规范化版本串**。该规则仅用于**资产版本**，包版本不再沿用。
- **D27（Q2d=a）**：非法版本号 ⇒ 编辑器**拒绝提交**；加载期该资产判**非法**（不生成、进报告）。
- **D28（Q2e=a）**：GUID 派生＝**包 ID ＋ 资产种类 ＋ 局部 ID ＋ 资产版本**；**不含包版本**。
- **D29（Q2f）**：包版本＝**hash(包 ID ＋ 包内元数据)**，**不含时间戳**（确定性、内容异构即可区分）；存 `manifest.version`；新建临时包时加 `-tmp`。
- **D30（Q2f-3）**：提供**显式"转正"API**：更新 lock（依赖与版本）→ 去掉 `tmp`；**没有独立导出点**——编辑器生成临时卡包时直接复制文件，发布即目录拷贝。转正即"手动更新 lock"的入口。
- **D31（Q2g=a）**：**废弃包级 `dependsOn`**；同 ID 包**可并存**，只要**资产不冲突**（同一资产同一版本 GUID 冲突才拒绝）。
- **D32（Q2h=a）**：lock **不记包版本**，只记包 ID ＋ 资产 GUID 集合。包版本退化为**内容指纹**（展示/诊断），防混用实际由资产 GUID 冲突承担。
- **D33（Q4a=a）**：**双层**——①**资产加载器**（宿主级：元数据→lock 合并→拓扑分层→加载列表）②**卡牌加载器**（`LowLevel` 触发器：接收清单→装配＋合法性检测）。**触发粒度＝整批一次**（单项清单退化为单卡一次）；产出＝**报告 ＋ 卡牌引用列表**。对局初始化时**统一加载双方牌堆里的牌**，同时**保留局内加载路径**（token/升级等）。
- **D34（Q4b=a）**：加载器由**插件**声明并注册进受控集合；卡包元数据只能**引用已注册加载器**；**包不得自带加载器**（用户理由：自带加载器的表达力没有超出"插件声明加载器"）。
- **D35（Q4c=a）**：合法性检测套件＝**引擎内置标准套件**（三档骨架固定）；插件/加载器只能**追加检查项**，不得改变三档骨架。
- **D36（Q4d=a）**：加载的是**卡牌资产/定义**，产出「应用层 ID → 已装载资产版本」引用表（并入中间层）；对局**按需实例化**。**实例化不再考虑任何依赖**——依赖解析/拓扑/脚本编译全部前置到加载阶段；实例化时只做纯装配，并**生成并加载效果**（把效果主触发器挂到合适位置）。
- **D37（Q4d-1）**：报告按**资产去重**，附"被哪些卡组条目引用"的计数。
- **D38（Q4d-2=a）**：牌堆中遇到非法资产 ⇒ **该卡位留空、开局继续**，报告标非法。
- **D39（Q4d-3）**：局内加载路径（token/升级/老兵）同样产出引用表条目并**更新中间层**。
- **D40（Q5-1 同意）**：判定表定稿——非法＝`id` 缺失／`factionCost` 缺失／`typeCategory` 缺失／单位 `battleStats` 缺失／指令反制 `effects` 缺失／`effects` 引用不存在／版本号非法；警报＝`name` 缺失／卡图缺失／描述缺失／`tagData` 缺失／未知词条。
- **D41（Q5-2）**：卡级聚合＝**任一非法项即整卡非法**；"留空"＝写入**类型默认值**（0/null/空串），读取方必须容忍；**报告携带字段描述**（字段路径／期望类型／默认值），为后续自动补全留出载体。
- **D42（Q5-3=a）**：包级门禁＝只拒绝**结构性非法**（清单/元数据/lock 不合法）；卡级警报与非法卡只进报告、不阻断包。
- **D43（Q5-4）**：报告**不落盘**，仅经 API/工具返回。
- **D44（用户新增方向）**：未来要建立**自动补全机制**，把值应用到残缺卡上，以支持"对局内生成随机卡牌"；报告的字段描述是该机制的输入载体。
- **D45（Q5-5=a）**：自动补全/随机卡生成**不在本次范围**；本次只保证**报告字段描述定成稳定 schema**（补全的输入契约）。
- **D46（Q3a=a）**：sidecar 命名＝`<源文件名>.meta.json`，同目录，一对一可逆映射。
- **D47（Q3b 同意）**：sidecar 结构＝`{ schemaVersion, packageId, source, assets[] }`；`assets[]` 条目＝`{ guid, kind, id, version, anchor, loader?, dependsOn[], conflictsWith[] }`；内含资产 GUID 独立、版本继承宿主、anchor 指向 `stableKey`／事件 `id`；`dependsOn` 引用＝`kind ＋ 应用层 ID ＋ 版本约束`（应用层 ID 全局唯一，跨包由前缀保证）。

- **D49（Q3d 同意）**：元数据沿用**读宽写窄**。
- **D50（Q3e 同意）**：manifest＝`{ schemaVersion, id, kind, name?, version, metadata: [sidecar 路径…] }`，即**元数据列表容器**。

## 代码 ↔ 陈述矛盾（需仲裁，不算实现问题）

### C1: 资产身份分层 vs 现有资产名文法
本次要求"为**卡牌/效果/触发器/handler** 声明 GUID 和元数据"＝按**资产种类**分型；现有 `AssetName` 的类型名是**加载方/来源**（json/csx/asm），只能表达文件级身份。同一个 `*.prefab.json` 内声明 1 效果 ＋ N 触发器 ＋ M handler，现有文法无法表达这四类各自的身份。

### C2: 版本粒度与格式冲突
现有资产版本＝**包版本**（`AssetNameOf` 继承），且 `AssetVersion` 强制 `x.y.z`；本次要求"卡牌元数据自持版本管理"且编辑器允许"版本号段数格式不限"。两者不能同时为真：包版本与卡牌版本谁是权威？`AssetVersion` 是否要放宽到 N 段？

### C3: 元数据载体自相矛盾
"为资产文件（含 csx/json）声明**元数据文件**，存在内含资产的元数据"指向 **sidecar（每文件一份元数据）**；"对于卡牌，**元数据存在卡牌就存在**"指向 **内嵌（卡文件内）**。同一套机制两种载体，需仲裁（并明确：卡牌是否也要 sidecar）。

### C4: "卡牌加载器＝底层触发器"与装载时机冲突
包级加载（`CardPackLoader.Load`→`Attach`）**必须早于 `Match.Initialize`**，此刻 `TriggerLayer.LowLevel` 触发器尚不存在（`Match.Initialize` 内才登记）；而 `LowLevel` 触发器只在**对局内**可用。=> 触发器形态只能承载"对局内的卡牌实例化/装载"，不能承载"包→定义集"的文件级加载。需仲裁"卡牌加载器"指哪一段，以及触发器化后的引导顺序。

### C5: 三档严重性 vs 现有"双零门"
本次要求"警报仍生成卡牌、非法才不生成"；现有卡包装载是 Errors=0 **且** Warnings=0（任一告警整包失败，`CardPackLoader.cs:57-64`）。包级门禁必须重定义（否则警报卡直接让整包不可加载）。

### C6: "非法不生成卡牌示例"措辞歧义
"（简单三字段：合法，警报和非法，非法不生成卡牌示例）"可读作 a) 非法卡不生成卡牌、也不生成占位示例；b) 非法卡仍生成一个示例占位卡供预览。

### C7: 依赖判定缺少状态模型
所述"已加载的资产"与"**注册但未加载**的资产"两态，现有代码只有"发现(Discovered)/解析(Resolved)/已装载(Loaded)"，**无"已注册未加载"**。该状态由谁产生（元数据注册表？）、何时转正，需定义。

### C8: GUID 与版本的关系歧义
"为每一个元数据都生成 GUID（需要包含所属卡包/插件的 ID，版本号这些，放在元数据里）"——是 a) GUID 纯随机、包ID/版本作为元数据**并列字段**；还是 b) GUID **确定性派生**自（包ID＋版本＋资产名）？若是 b，升版即换身份，依赖锁定与"卡牌版本管理"会互相破坏。

### C9: 两个 lock 文件的内容边界
"描述当前卡包版本内所有资产的 GUID"是否含**内含资产**（触发器/handler）；"从所有资产依赖里拉取依赖资产的 GUID"是否含**跨包传递依赖**与**包版本**（只锁 GUID 无法复现版本组合）。

### C10: 编辑器版本号语义重叠
"进入编辑器生成**临时版本号**"＋"保存时**生成新的版本**"＋"允许**手写版本号**（必须递增）"三者作用对象不同（包？卡牌？效果？），且临时版本号是否参与 lock 未定。

### C11: "编辑器表达力全部由后端承担"的 API 形态
后端编辑器 API 是**文本级读写**（前端拿到 JSON/csx 原文直接改）还是**结构化读写**（字段级 model）？这决定前端与 agent 的可用边界，也决定"直写资产文件指针"的合法性。

### C12: "沙盒内置编辑器"的形态
"内置"＝进程内后端组件 ＋ 一组 `editor.*` MCP 工具（受 Authoring 档门控）？还是独立编辑器进程/工程？与现有 47 条工具、`sandbox.create` 固定单包脚手架的关系未定。

### C13: 冲突管理语义缺失
"依赖和**冲突**管理全部放在元数据里"——冲突声明粒度（GUID / 资产 ID / 版本区间）、冲突时行为（拒绝加载整包 / 择一 / 仅告警）均未定义。

### C14: 卡包＝"元数据列表容器"与 manifest 的关系
现有 `manifest.json` 已含 `assets[]`（文件清单）。新形态下 manifest 是否保留？"元数据列表"是 manifest 内**引用**各 sidecar 元数据，还是 manifest **内联**全部元数据？

### C15: 效果/触发器元数据"仅 ID 和依赖"与第一句冲突
第一句要求四类资产都"声明 GUID 和元数据"；第二句说效果/触发器"元数据仅表达其 ID 和依赖"。=> 是否意味着**效果/触发器没有独立 GUID**（其 ID 即身份），只有卡牌有 GUID？

### C16: 既有资产迁移
19 张卡 ＋ 14 个 prefab ＋ 0 个 csx 需补元数据/GUID；`card-pack-demo`/`card-pack-diy` 连 manifest 都没有。是硬切（旧资产无元数据即非法）还是提供一次性迁移工具（自动生成 GUID/元数据）？

### C17: 版本级 GUID 与"依赖"语义互斥（D2 派生）
GUID 随版本重派生后，若依赖直接引用 GUID，则依赖被钉死在某一版本；而现有 `PackageResolver` 是"约束择版"（`AssetVersionConstraint`＋`SelectHighest`）。需要区分"声明期引用"与"解析期锁定"，否则双 lock 文件没有存在意义。

### C18: D1（统一 sidecar）与原句"元数据存在卡牌就存在"（D1 派生）
内嵌语义下"卡在则元数据在"是物理同一；sidecar 下两者是两份文件，必须定义宿主缺失、meta 缺失、孤儿 meta 三态。见 Q1d。

### C19: "多版本注册、只加载一个"与现有注册面冲突
现有 `CardLibrary.Register(id, definition)` 以**局部 id 为键**，同 id 第二份即冲突；`EngineHost` 则把所有包的全部资产无条件装入目录（无"择一加载"）。D2 的"多版本注册"需要新的键（版本级）与新的择版面，不能复用现有卡库键。

### C20: "层内按 ID 字典序"与"不考虑层内顺序、先到先得"互斥（Q16 派生）
同一轮里选了 1b（局部 ID 字典序），又声明"二维列表不考虑层内顺序（先到先得），只考虑层间顺序"。前者承诺层内**全序且与注册顺序无关**，后者承诺层内**就是算法入队序**。二者对增量重载的比对方式有实质差异（逐位比对 vs 集合比对）。

### C21: 测试前缀与"编辑已有资产"互斥（D15 派生）
第 5 条要求"玩家可选择**已有资产**来编辑"。若测试资产强制加前缀，则"改一张已有卡"产出的是一张**另一个 ID 的新卡**，卡组引用的旧 ID 仍然解析到正式版——编辑无法在试玩中生效。若允许测试资产与正式资产**同局部 ID**，则与 `CardLibrary` 同键拒绝（C19）以及"正式/测试两域"的隔离边界冲突。

### C22: 包版本含时间戳 vs GUID 含"版本号"（D2 × D24 派生）
D2 说 GUID 派生包含"所属卡包/插件的 ID、版本号"；D24 说包版本＝hash(…＋**时间戳**)。若 GUID 里的"版本"取**包版本**，则每次保存都换时间戳 ⇒ 包内**全部资产 GUID 变化** ⇒ 所有引用它们的 lock 立即失效，"lock 只能手动更新"变成"每次保存必须全量重锁"。必须裁定 GUID 里的版本取**资产版本**（Q2e）。

### C23: "保存＝复制/覆盖文件"与"保留历史版本条目"冲突（D7 × D30 派生）
D7 要求保留旧版本条目（旧 lock 仍可解析）；D30 说编辑器生成临时包时**直接复制文件**、保存时转正。若保存＝用临时包覆盖原包目录，旧版**源文件内容**被替换，而 lock 里仍记着旧 GUID ⇒ 注册表找不到对应内容 ⇒ 旧 lock 必然失效，"保留历史版本"变成一句空话。保存的写入形态必须裁定（Q23a）。

### Q32: asm 插件资产的历史版本 【Completed — D64】

### Q34: 本次迁移范围 【Completed — D65：框架 ＋ core 试点】
- 全面资产化的工程量集中在"内置插件声明其全部服务资产 + 生成清单/lock"。
  - a) **框架 ＋ `orc.builtin.core` 试点**：跑通"声明→清单→双 lock→启动校验→依赖"，其余两个插件留批次。（推荐）
  - b) 框架 ＋ 三个内置插件全量迁移（判定器 20+／词条 19／组件 6／行动契约／投影）。
  - c) 只做框架与工具，内置插件保持 asm 兼容现状。

#### 事实基线（验收取证）
- 三个插件包（`orc.builtin.core` / `orc.foundation.actions` / `orc.builtin.ui`）目录下**只有 v1 `manifest.json`**：无 sidecar、无 lock；`version` 仍是 `1.0.0`（非内容指纹）、`dependsOn` 仍在使用（已退役字段）、`assets: []`。
- 插件资产由**程序集代码注册**（`LoadedPluginScript(pre/post/process)`）：判定器、资产服务、词条、卡组件、效果 handler——经 `PluginRegistrationContext` / `ProcessRegistrationContext` 落地。
- 装载序改为**代码内** `BuiltInPluginPackage.LoadOrder`（`PluginLoadOrder`；三项启动断言），**不进 manifest**。
- `AssetKind` 只有 card/effect/trigger/handler —— **无法表达判定器/资产服务/词条/卡组件**。
- sidecar 命名规则是「`<源文件名>.meta.json`」——程序集没有可挂的"源文件"。
- 实现侧理由（`implementation.md` S4 Rationale）："插件装载序由资产拓扑决定"是**推导而非意图**，插件无 lock/sidecar，资产拓扑在其形态上无定义。

#### 选项
- **a) 插件豁免（实现现状）**：把 R3/R7 的「包」限定为 `cardpack`；插件只保留 manifest ＋ 代码内 `LoadOrder`，不参与 sidecar/lock/资产拓扑。改需求与 CONTEXT，代码不动。
- b) **插件只生成两个 lock**（不生成 sidecar）：需先为程序集资产分配 GUID（程序集名＋资产类型名派生）、定义"插件资产清单"的载体；lock 只作复现记录。
- c) **插件全面纳入**：扩展 `AssetKind`（judicator/assetservice/keyword/component…）、为程序集生成 meta、双 lock、依赖资产级。成本最高。
- d) 插件资产改 csx 重写以走 sidecar —— 不可行（内置判定器需访问游戏层内部类型）。
